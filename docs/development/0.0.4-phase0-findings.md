# SignalLayer CoreOS 0.0.4 Phase 0 findings

**Status:** PHASE 0 FINDINGS — ARCHITECTURAL REVIEW REQUIRED

**Measured:** 2026-10-19 on `slit-coreosdev-01`, Fedora 44 x86_64

**Repository baseline:** `1674cc4` (merged PR #22)

**Pinned base:**
`ghcr.io/transitionalcomputing/signallayer-base@sha256:ef8a660e5b1aa24f8b35c43caa57e972f280766c7980440f4490193bf987df2c`

**Pinned base image ID:**
`d312275bca51c0a0e28a30b5fe75d8027f540a21713934b84a35f77174e3ef7b`

This report records the read-only investigation required by
[the 0.0.4 plan](../milestones/0.0.4-plan.md). It does not authorize or claim
Phase 1 implementation. Terms have the following meanings:

- **MEASURED:** observed directly in the pinned image or existing builder.
- **DOCUMENTED:** stated by the exact installed man page or authoritative
  upstream documentation.
- **PROPOSED:** recommended for architectural approval; not implemented.
- **DEFERRED:** requires a Phase 1 image and genuine-KVM runtime evidence.

## Executive finding

No fundamental Fedora 44 dependency blocker was found. The pinned base already
contains the complete candidate runtime set, including Podman, Quadlet, crun,
conmon, container-selinux, `pasta`, subordinate-ID helpers and overlay helpers.
Phase 1 should use and assert those pinned-base versions rather than update from
moving Fedora repositories.

Podman 5.8.7 supports the required rootless Quadlet and security-label keys.
The shipped containers/storage configuration already names
`/usr/lib/containers/storage` as a read-only `additionalimagestores` path.
The feasibility of a dedicated SELinux process domain and data type is supported
by the installed policy interfaces, but the actual transition and equal-MCS
isolation remain Phase 1 loaded-policy gates.

Phase 1 is **ready for architectural review, not yet authorized**. Approval is
required for the proposed identity, subordinate ranges, immutable Quadlet
indirection, network/storage choices and reconstructible-metadata rule below.

## 2. Rootless identity and subordinate mappings

The pinned base is **MEASURED** with system UID/GID allocation ranges 201–999.
UIDs 977–999 and nearby GIDs are occupied; UID and GID 976 are free. Existing
SignalLayer service identities use dynamic sysusers allocation and no maintained
file reserves 976. The base has empty `/etc/subuid` and `/etc/subgid`. The
builder's `coreos` account already owns `524288:65536`, which is also the
`SUB_UID_MIN`/`SUB_GID_MIN` recorded by the pinned base.

**PROPOSED identity:**

| Property | Value |
| --- | --- |
| Account/group | `sl-management` / `sl-management` |
| UID/GID | `976:976` |
| Shell | `/usr/sbin/nologin` |
| Password | locked |
| Home/control root | `/var/lib/sl-management`, root-owned and not generally writable by the account |
| Subordinate UID range | `589824:65536` (589824–655359) |
| Subordinate GID range | `589824:65536` (589824–655359) |
| Future reservation | start `sl-runtime` at 655360 or later; do not share the management range |

The range begins immediately after the builder's `coreos` allocation and is
aligned to the Fedora default 65,536-ID extent. Every build and first boot must
reject a UID, GID or subordinate-range collision. A future base refresh must
re-run the collision check because Fedora may add system identities.

**PROPOSED provisioning:** use an explicit-ID sysusers record for the account
and group; ship exact root-owned `sl-management:589824:65536` entries in both
subordinate-map files. Sysusers does not provision subordinate maps, and
automatic `useradd` allocation would not be deterministic. Phase 1 must prove
bootc `/etc` merge behavior, idempotence and collision failure before this
mechanism is accepted.

Writable graph, cache and application-data directories must be explicit
children. The account must not own its Quadlet/configuration search path or be
able to create `$HOME/.config/containers/systemd` overrides.

## 3. Quadlet and user-manager startup

The installed Quadlet 5.8.7 man page and generator **MEASURED** the following:

- cgroups v2 is mandatory;
- rootless Quadlets require a real user manager and cannot be made rootless by
  setting `User=`, `Group=` or `DynamicUser=` on a system Quadlet;
- rootless search paths are `$XDG_RUNTIME_DIR/containers/systemd`,
  `$XDG_CONFIG_HOME/containers/systemd`, `~/.config/containers/systemd`,
  `/etc/containers/systemd/users/<UID>` and
  `/etc/containers/systemd/users`;
- this version has no distribution rootless search path below `/usr/share`;
- Quadlet supports symbolic links within its search paths; and
- `QUADLET_UNIT_DIRS` is documented for bounded generator debugging, not as the
  proposed production bootstrap mechanism.

This conflicts with the contract's candidate
`/usr/share/containers/systemd/users/<uid>` path. **PROPOSED:** keep the
authoritative `.container` file in immutable `/usr/share/signallayer/quadlet/`
and ship a root-owned symlink at
`/etc/containers/systemd/users/976/sl-management.container`. The runtime user
cannot replace either object. A/B/A tests must prove the `/etc` symlink resolves
to the active deployment's `/usr` content.

systemd 259 documents that lingering starts the user manager at boot and keeps
it alive without a login. An image-owned tmpfiles marker under
`/var/lib/systemd/linger/sl-management` remains **PROPOSED**: the no-login,
first-boot ordering and marker-loss behavior are **DEFERRED** to Phase 1 KVM.
No release procedure may require a manual `loginctl enable-linger` step.

## 4. Immutable management image store

The pinned `/usr/share/containers/storage.conf` is **MEASURED** with:

```toml
[storage]
driver = "overlay"

[storage.options]
additionalimagestores = [
  "/usr/lib/containers/storage",
]
```

The base already carries an empty, root-owned store skeleton at that path with
`overlay-images/images.lock` and `overlay-layers/layers.lock`. The exact
containers/storage documentation defines `additionalimagestores` as normally
read-only and supports rootless overlay. It also warns that a per-user
`storage.conf` replaces, rather than merges with, system configuration.

**PROPOSED:** use the existing `/usr/lib/containers/storage` location rather
than introduce `/usr/share/signallayer/management-image-store`. Populate one
verified digest during the CoreOS build and leave the store read-only at
runtime. Prohibit a user-owned `storage.conf`; use a root-owned fixed
configuration so `additionalimagestores` cannot be removed or redirected.

Feasibility is positive, but ownership is security-sensitive. A root-created
store must be traversable/readable by the rootless runtime without globally
weakening layer contents. Upstream documents `force_mask=shared` for shared
stores but warns that it makes all image files host-readable and requires a
mount program. That is not accepted by Phase 0. Exact DAC, UID mapping, xattrs,
SELinux labels and rootless usability are **DEFERRED** to Phase 1.

## 5. SELinux isolation mechanism

The pinned `container-selinux` package is **MEASURED** to provide:

- `container_domain_template(prefix, file_prefix)` for a custom container
  process domain;
- `container_manage_files_template` and the `container_file` interface;
- generic `container_t` MCS separation; and
- `container_ro_file_t`, `container_file_t` and container storage/runtime types.

The runtime-domain template is not appropriate for the management process: its
installed definition includes broad runtime authority such as raw fixed-disk
access. **PROPOSED:** define a dedicated management *container process* domain
with the ordinary container-domain template and a dedicated persistent-data
type. Do not classify the management process as a container runtime.

The generic `container_file_type` attribute may give other container domains
access when MCS levels match. Therefore the dedicated data type must not be
added to a broad container file attribute unless the generated policy is shown
to deny a generic `container_t` process deliberately assigned the same MCS
categories. Policy-source compilation alone is insufficient.

The base's default file-context mapping for `/usr/lib/containers/storage` is
`lib_t`, and `/var/lib/sl-management/...` defaults to `var_lib_t`. Explicit
maintained file contexts are required for both the immutable image store and
writable engine/data paths.

**DEFERRED:** loaded enforcing transition, entrypoint access, rootless runtime
relabel behavior, same-MCS cross-domain denial, restart/reboot context stability
and A/B/A rollback stability.

## 6. Quadlet security-label directives

Podman 5.8.7 **MEASURED** support for:

```ini
SecurityLabelType=sl_management_t
SecurityLabelFileType=sl_management_data_t
```

A disposable `--dryrun` generated exactly:

```text
--security-opt label=type:sl_management_t
--security-opt label=filetype:sl_management_data_t
```

The same test confirmed `Pull=never`, `ReadOnly=true`,
`NoNewPrivileges=true` and `DropCapability=all` translate to fixed Podman
arguments. The label directives select types; they do not create policy,
authorize a transition, label pre-existing bind-mounted data or prove that the
loaded policy preserves isolation. Those behaviors remain **DEFERRED**.

## 7. Networking and storage selection

### Networking

The pinned configuration **MEASURED** `rootlessNetworkCmd: pasta`; `pasta` is
present while `slirp4netns` is absent. A Quadlet dry-run confirmed
`Network=pasta` becomes `--network pasta`. Netavark and Aardvark are installed
for Podman's broader network backend, but the minimal management fixture needs
no bridge network, inbound publish or DNS service owned by Aardvark.

**PROPOSED:** specify `Network=pasta` explicitly, publish no ports, and permit
only the measured outbound/DNS behavior required by the fixture. Do not rely on
an implicit default or install `slirp4netns`. Phase 1 must prove private
namespace identity, host-loopback isolation, offline startup and fail-safe
behavior if `pasta` is absent.

### Storage

The builder's rootless Podman already uses native overlay successfully on XFS;
the pinned base uses overlay by default and carries kernel 7.2.7. This is useful
feasibility evidence, but the builder is not the guest.

**PROPOSED:** select native rootless overlay and explicitly reject silent VFS or
`fuse-overlayfs` fallback. Keep `fuse-overlayfs` installed because it is already
in the pinned base, but do not configure it unless the genuine-KVM Phase 1
candidate proves native overlay cannot satisfy the contract and the design is
reviewed. Record the actual guest backing filesystem, graph status and driver.

## 8. Runtime reconstruction

The immutable image store, image-owned Quadlet and persistent application data
must be three separate authorities:

| State | Proposed location/owner | Recovery rule |
| --- | --- | --- |
| Accepted image and image metadata | `/usr/lib/containers/storage`, CoreOS root, read-only | Replaced and rolled back with the OS deployment |
| Engine graph/container metadata and writable container layer | `/var/lib/sl-management/containers/storage`, `sl-management`, dedicated runtime label | Reconstructible only while stopped; never authoritative application data |
| Runroot | `/run/user/976/containers`, user manager | Ephemeral each boot |
| Management application data | `/var/lib/sl-management/data`, dedicated management-data type | Preserved across reconstruction, update and rollback |
| Root-owned compatibility/recovery record | separate native recovery path | Records image digest, runtime/storage version and last accepted state |

**PROPOSED reconstruction:** stop the exact user manager/container unit; verify
that application data is a separate bind mount; quarantine or recreate only
the engine graph/runroot; start from the active deployment's immutable image
store and fixed Quadlet; verify the expected digest before admitting healthy
state. Reconstruction must be an explicit native recovery action, not an
automatic response to every startup error.

Whether an empty writable graph can consume the bundled image store, recreate
container metadata and preserve the application bind mount is **DEFERRED** to
Phase 1. No destructive reset was run during Phase 0.

## 9. Rollback compatibility

The pinned base and current Fedora repositories already differ at Podman 5.8.7
versus 5.8.9. A later B deployment can upgrade containers/storage metadata,
network state, generated units or labels in ways an older A deployment cannot
read. No backward-storage-schema guarantee was established in Phase 0.

**PROPOSED rules:**

1. never update runtime packages independently of the CoreOS deployment;
2. record Podman, containers-common, graph driver and state-schema identity;
3. keep application data outside Podman's graphroot and named-volume metadata;
4. on incompatible metadata, fail closed and keep native CoreOS recovery
   available;
5. rebuild only disposable engine metadata from the active deployment's
   immutable image store; and
6. do not let B irreversibly migrate application data without a separately
   versioned forward/backward migration contract.

Phase 1 must prove stop/reconstruct/start within one deployment. Full A→B→A
storage, label and state compatibility remains a later genuine-KVM release
gate.

## 10. Decisions and Phase 1 prerequisites

### Recommended dispositions

| Decision | Phase 0 recommendation |
| --- | --- |
| Runtime packages | Assert the pinned-base installed NEVRAs; no moving-repository update |
| Identity | `sl-management` UID/GID 976; reserve `sl-runtime` separately |
| Subordinate IDs | UID/GID `589824:65536`; collision failure mandatory |
| Storage | native rootless overlay; no silent VFS/FUSE fallback |
| Network | explicit `pasta`; no published port |
| User manager | declarative lingering candidate, KVM proof required |
| Quadlet | immutable `/usr` source via root-owned `/etc/containers/systemd/users/976` symlink |
| Image delivery | CoreOS-bundled `/usr/lib/containers/storage`, digest verified; no registry dependency at boot |
| SELinux | dedicated container process domain and dedicated data type; never runtime-domain template |
| Recovery | exact native action reconstructs only disposable graph/runroot |
| Persistent data | separate bind-mounted, typed application directory |
| Rollback | fail closed on schema mismatch; reconstruct graph from active deployment |

### Review items before Phase 1 authorization

1. Approve UID/GID 976 and subordinate range 589824–655359.
2. Approve the immutable Quadlet source plus root-owned `/etc` symlink, because
   Podman 5.8.7 lacks a rootless `/usr/share` search path.
3. Approve `/usr/lib/containers/storage`, native overlay and explicit `pasta`.
4. Approve the dedicated process/data type direction while retaining all
   loaded-policy proof as a hard Phase 1 stop condition.
5. Define the minimal non-product fixture's digest, entrypoint, health result
   and compatibility field before building it.
6. Define exact graph reconstruction command/API and resource limits before it
   becomes a native recovery operation.
7. Correct the approved contract's startup diagram text from `sl-runtime user
   manager` to `sl-management user manager`; `sl-runtime` remains reserved.

No Podman socket, rootful container, host network, broad volume, unconfined
label, generic systemd control or second machine authority is required by these
recommendations. If any becomes necessary during Phase 1, stop for contract
review.

## Reproduction summary

All target-image measurements used the already-present pinned image with
`podman run --rm --pull=never`; package-version queries used either
`--network=none` or repository metadata in a disposable container. No packages
were installed, no image was pulled or built, and all temporary container
directories were removed with their containers.

Representative commands:

```bash
IMAGE=ghcr.io/transitionalcomputing/signallayer-base@sha256:ef8a660e5b1aa24f8b35c43caa57e972f280766c7980440f4490193bf987df2c

podman image inspect "$IMAGE"
podman run --rm --pull=never --network=none "$IMAGE" rpm -q \
  podman crun conmon container-selinux systemd containers-common \
  netavark aardvark-dns passt fuse-overlayfs shadow-utils shadow-utils-subid
podman run --rm --pull=never "$IMAGE" dnf -q repoquery \
  --latest-limit 1 podman crun conmon container-selinux systemd
podman run --rm --pull=never --network=none "$IMAGE" \
  /usr/libexec/podman/quadlet --version
podman run --rm --pull=never --network=none "$IMAGE" sh -c \
  'grep -n additionalimagestores /usr/share/containers/storage.conf'
```

The Quadlet translation tests used `QUADLET_UNIT_DIRS` only inside a disposable
container with the documented generator `--user --dryrun` mode. No container
workload was started by those tests.
