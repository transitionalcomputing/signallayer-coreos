# SignalLayer CoreOS 0.0.4 — Phase 1 Pass 3 execution plan

**Status:** PROPOSED — requires product-owner architecture and security approval
before production CoreOS surfaces change.

**Input evidence:** Candidate C disposable feasibility, 28/28 PASS at
`4e5f3ecba89dcaa6205aa3b86995d50ac81ba5ee`.

**Outcome:** turn the measured Candidate C mechanism into an attributable
production candidate and prove packaging, confinement, networking, trusted
reset and deployment compatibility without adding workload orchestration.

**Release-Identity:** none during contract and implementation review; a later
artifact-validation pass must name the planned OS release identity.

**CoreOS-Surface-Change:** pending approval. Expected surfaces are runtime
packages, one locked identity and subordinate maps, fixed root-owned units,
root-owned configuration/oracle files, deployment-owned rootfs content,
persistent runtime/data directories and dedicated SELinux policy. The exact
inventory diff must be reviewed before implementation.

## Gate P3-0 — approve the production contract amendment

Submit one focused contract change that:

1. adopts deployment-owned immutable rootfs execution as the selected Candidate
   C mechanism and removes incompatible immutable-OCI-store requirements;
2. names the exact fixed runtime, verifier and recovery units and their ordering;
3. separates permanent spawn prohibitions from temporary reset inhibition;
4. defines verifier activation without a user manager and preserves system-slice
   cgroup supervision;
5. fixes the rootfs/oracle, compatibility-epoch, application-data and disposable
   engine-cache ownership model; and
6. records exact networking and SELinux acceptance boundaries.

No runtime implementation begins until the product owner approves this
amendment and its inventory/security consequences.

## Work package P3-1 — production packaging and identity

Implement the approved package set and build an attributable minimal rootfs in
the CoreOS deployment. Generate a root-owned manifest/oracle from normalized
paths, types, modes, ownership, capabilities, xattrs, SELinux expectations and
content hashes. Provision `sl-management` and collision-safe subordinate maps
idempotently, including occupied, malformed, partial and repeated cases.

Cheap gates before image build:

- source-inventory and build-contract update with an explicit diff;
- rootfs manifest positive fixture plus missing, extra, modified, symlink,
  wrong-owner, wrong-label and special-file negative fixtures;
- identity collision/overlap/interruption/retry tests; and
- exact fixed-command, path, environment and prohibited-feature assertions.

Stop if rootfs content depends on machine-local numeric ownership, if an
untrusted identity can alter the oracle/bootstrap, or if construction cannot be
bound to the booted deployment.

## Work package P3-2 — dedicated SELinux boundary

Define only the approved runtime process, immutable rootfs, disposable cache
and persistent application-data types. Compile the policy and query the loaded
policy before runtime acceptance. Test transition, no-transition execution,
type spoofing, unauthorized relabel, equal-MCS generic-container access with DAC
made permissive, and denial of credentials, host filesystems, devices, journals,
systemd control and policy management.

AVCs are evidence. Stop rather than grant broad filesystem, device, credential,
systemd or SELinux-policy authority. Never use blind `audit2allow`, disable
labels, or make the runtime permissive.

## Work package P3-3 — explicit rootless networking

Pin the approved Fedora `pasta`/`passt` path and fail closed on missing helper,
unexpected backend, route failure or DNS failure. Measure outbound DNS and
egress separately from host loopback, host addresses, guest services and
listeners. Inventory every namespace, route, address and listening socket.

The acceptance candidate must expose no Podman socket or inbound listener and
must not use host networking. The precise allowed egress/DNS and host-reachability
policy is an owner decision at P3-0.

## Work package P3-4 — trusted verifier and reset transaction

Implement a root-owned verifier that completes before any Podman command. It
must bind the booted deployment, oracle and compatibility epoch; reject any
mismatch; and select only that epoch's graphroot. Implement a fixed recovery
transaction independent of Podman that:

1. acquires an exclusive transaction lock and inhibits new fixed-unit starts;
2. stops the exact runtime and proves its cgroup/processes are gone;
3. re-verifies mount identity, path ancestry, oracle and epoch;
4. atomically quarantines only the verified disposable cache;
5. reconstructs cache from the immutable deployment rootfs;
6. preserves application-data hashes, ownership, mounts and labels; and
7. re-verifies before allowing the fixed service to start.

Negative tests cover concurrent starts, stale/in-flight starts, symlink and
mount substitution, wrong epoch, interruption at every state boundary, full
disk, corrupt oracle/rootfs/cache, Podman absent and repeated recovery. A reset
that can delete application data or relies on Podman is rejected.

## Work package P3-5 — bounded KVM acceptance

After all cheap gates pass, build one enforcing candidate and run one genuine-
KVM acceptance. It must prove packaging identity, fixed-command rootless
startup, loaded SELinux enforcement, approved networking, failure isolation,
trusted reset and independent native console/Platform/update/rollback health.
Every material assertion requires a negative control; missing evidence is
UNPROVEN.

## Work package P3-6 — A-to-B-to-A lifecycle

Build attributable A and B deployments with explicit compatibility epochs. Use
the existing fixed Platform lifecycle to stage and activate B, make the registry
unavailable, select retained A and activate exact A. Across both transitions,
prove:

- deployment, rootfs/oracle and epoch identities;
- neither deployment opens or migrates the other's incompatible graph;
- compatible refusal occurs before Podman and leaves native recovery healthy;
- `sl-management` mappings and application-data hashes/labels persist;
- disposable cache reconstruction is non-destructive; and
- SELinux, immutable root, console, Platform operations and clean shutdown stay
  accepted.

This lifecycle is not evidence-reusable from Candidate C because production
packaging, policy and epoch behavior are new.

## Completion and stop conditions

Pass 3 is complete only when P3-0 through P3-6 have reviewable source,
machine-readable evidence and independently reviewed negative controls. Stop
for owner review if implementation requires a Podman socket, rootful fallback,
host networking, general command/unit selection, writable deployment rootfs,
broad SELinux authority, a second machine authority, or destructive recovery.

General workload lifecycle, Management Plane APIs and role behavior remain
deferred beyond 0.0.4.
