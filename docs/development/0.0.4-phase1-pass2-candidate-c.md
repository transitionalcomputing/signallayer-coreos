## Measured result

The Fedora 44 guest used Podman 5.8.7 and crun 1.28. A root-only setup step
materialized the existing harmless fixture into the disposable overlay,
created the minimum standard rootfs mount targets, set root ownership and
`container_file_t`, and exposed the tree through a read-only bind mount. A
fixed system service then invoked rootless Podman as locked `sl-management`
with exact `--rootfs` input, `--network=none`, `--read-only`, no-new-privileges,
all capabilities dropped, and no caller-controlled command or path.

Observed runtime properties included subordinate UID/GID mapping, distinct
user/mount/PID/IPC/network/UTS namespaces, non-overlay container `/`, zero
effective/permitted/bounding/ambient capabilities, seccomp mode 2, no Podman
socket, and a process in the fixed system-service cgroup. The hostile per-user
containers configuration was ignored because all configuration paths were
pinned to root-owned files.

Stopping the service removed the `--rm` container. A launch using a missing
rootfs failed with exit 125; NetworkManager and `multi-user.target` remained
active, no failed units appeared, and the original fixed service subsequently
ran stably again. SELinux stayed Enforcing, no related AVC was found, both
read-only input hashes were unchanged, and QEMU exited cleanly.

## Ordinary defects corrected during the experiment

Three preserved early runs stopped before acceptance because the minimal
scratch rootfs lacked Podman's required mount targets: first `/etc`, then
`/etc/mtab`, then `/var`. The fixture preparation now creates only the standard
empty targets and files needed before the rootfs becomes read-only.

The next preserved run passed the runtime mechanism but scored 24/28 because
the evaluator expected `sl-platformd` to be active in the older Phase 1 base,
relied on empty Podman log output for process health, and sampled recovery too
early. The final harness instead measures the native multi-user target, the
running inspected fixture process, and three stable recovery observations.
Every one of the 28 final assertions has an offline negative control.

## Explicit boundary

packaging, trusted reset/verifier behavior, continuous spawn exclusion during
reset, dedicated production SELinux types, private rootless networking,
resource policy, general OCI lifecycle, Management Plane orchestration, or
CoreOS A-to-B-to-A update/rollback compatibility. Those claims remain
**UNPROVEN** and require separately authorized design and acceptance work.
