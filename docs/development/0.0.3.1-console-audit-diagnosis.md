# SignalLayer CoreOS 0.0.3.1 console/audit diagnosis

- **Status:** Pass 1 diagnosis complete; no production fix implemented
- **Date:** 2026-10-19
- **Result:** Reproduced on `ttyS0`; root cause confirmed
- **Recommendation:** GO for a narrowly scoped implementation and regression-validation pass

## Scope

This report diagnoses the v0.0.3 appliance-console disruption reported on
Proxmox VE. It does not change the operating system, SELinux policy, release
artifacts, or the published tag. The investigation branch is based on the exact
validated runtime source, not the documentation-only tag commit.

## Console and message routing

The image explicitly enables `sl-console@tty1.service` and
`sl-console@ttyS0.service`, masks the generic getty templates, and configures
both instances with `TTYPath=/dev/%I`, `StandardInput=tty-force`, and
`StandardOutput=tty`. This gives the appliance process the intended terminal
but does not exclude kernel-console writes.

The released command line contained:

```text
console=tty0 console=ttyS0 console=ttyS0,115200n8
```

The image's maintained disk configuration contributes `console=tty0` and
`console=ttyS0,115200n8`. Thus kernel output shares the virtual console and the
same serial device used by the two appliance instances. Runtime
`/proc/sys/kernel/printk` was `7 4 1 7`, so notice-level kernel records were
eligible for immediate console output.

Journald was not forwarding journal records to a console:
`ForwardToConsole` retained its `no` default. Persistent journald storage and
`Audit=yes` were active. The image did not contain `auditctl` or
`/etc/audit/auditd.conf`. The observed console lines came from the kernel audit
printk path, not journald console forwarding.

The console clears and renders once, then blocks in `read_line()`. It neither
owns an exclusive display channel nor repaints after asynchronous kernel
writes. Therefore a kernel message emitted after rendering displaces the UI
until a later operator action causes a redraw.

## Message-source trace

The `invalid_bootcinstall_testlabel_t` event is deliberate bootc behavior, not
an attempted persistent label. Exact installed-version source shows that bootc
creates a temporary file and runs `chcon -t
invalid_bootcinstall_testlabel_t` to test whether it has SELinux `mac_admin` /
`install_t` authority. bootc's own test metadata calls the resulting denials
expected and informational. On a composefs host, even `bootc status` enters
`prepare_for_write()` to establish its private mount namespace and runs that
preflight:

- [bootc 1.16.13 SELinux probe](https://github.com/bootc-dev/bootc/blob/v1.16.13/crates/lib/src/lsm.rs#L62-L76)
- [bootc 1.16.13 status initialization](https://github.com/bootc-dev/bootc/blob/v1.16.13/crates/lib/src/status.rs#L446-L454)
- [bootc's expected-AVC test annotation](https://github.com/bootc-dev/bootc/blob/v1.16.13/crates/xtask/src/tmt.rs#L1279-L1289)

The `sl_platformd_t` `{ write }` denial on the physical OSTree `objects`
directory is a separate negative writability query. The maintained policy does
not grant the write. Existing hardening evidence ties it to libostree's
`faccessat2(..., W_OK)` repository-open probe; bootc continues read-only. In
this run every Session1 status request succeeded despite that denial. No actual
repository mutation or unexpected label-scoped denial was observed.

The records recur because every Session1 `GetPlatformStatus` reaches Platform1
and launches fixed `bootc status --json`. The appliance console does this when
it refreshes. When remote management is enabled, `sl-remoted` also refreshes
Session1 initially, after invalidations, and every 60 seconds. This explains
persistent bursts without making `sl-console` itself an audit source.

Linux emits undelivered audit packets through `kauditd_printk_skb()` using
`pr_notice`; that is the console-visible path observed here. The kernel still
retains these messages and journald captured a more complete audit stream than
the rate-limited console output:

- [Linux audit printk path](https://github.com/torvalds/linux/blob/master/kernel/audit.c)
- [Linux printk console-level semantics](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/kernel.html#printk)

## Bounded reproduction

The existing boot harness booted the exact released qcow2 through a disposable
qcow2 overlay. The appended diagnostic probe only observed configuration and
issued five sequential, read-only Session1 status calls. It installed nothing,
changed no persistent guest state, and did not modify the source disk.

Host-side invocation was the maintained `tests/boot/boot-qcow2.py` with:

```text
--source-release /tmp/sl-console-diag/source-release
--source-image /tmp/sl-console-diag/source-image.json
--source-archive .../signallayer-coreos-0.0.3-x86_64.oci.tar
--ovmf-code /usr/share/edk2/ovmf/OVMF_CODE.fd
--ovmf-vars /usr/share/edk2/ovmf/OVMF_VARS.fd
--accel kvm --cpus 2 --timeout 300
```

The boot gate passed 18/18, the guest powered down cleanly, and the source-disk
checksum was unchanged. All five Session1 calls returned valid schema 0.4
status. The audit transport contained 14 intentional invalid-label records,
six `sl_platformd_t` OSTree writability denials, and two `initrc_t` `mac_admin`
denials caused by the harness's independent direct `bootc status` observation.

The serial chronology is direct reproduction evidence. At serial line 1460 the
appliance rendered `SignalLayer CoreOS`; beginning at line 1467 the terminal
received `kauditd_printk_skb`, `invalid_context`, syscall/proctitle, and the
`sl_platformd_t` OSTree denial beneath that UI. Kernel rate limiting suppressed
additional console callbacks, while journald retained the full audit records.
This proves visible displacement on the supported `ttyS0` appliance terminal.

The run did not capture a framebuffer screenshot of `tty1`. Its exposure is
strongly supported, rather than newly observed: the field report captured that
behavior, the exact release routes kernel output to `tty0`, and the appliance
owns `tty1`. The duplicated serial console argument and one harness-induced
`Busy` UI message were observed but are not causes of the audit displacement.

## Root cause

**Confirmed primary cause:** the appliance UI and kernel printk output share the
same terminals, while the UI does not redraw after asynchronous writes. The
release console loglevel admits audit's notice-level printk records.

**Confirmed trigger:** read-only platform status invokes bootc 1.16.13. Its
intentional invalid-label authority probe and libostree's denied `W_OK` query
produce audit records. Repeated Session1 consumers repeat those probes.

**Not found:** an actual unauthorized OSTree mutation, a requirement to weaken
SELinux, or journald forwarding records to the console. The additional
`sl-console` and systemd records visible in the field screenshot were not all
individually classified by this bounded run; ordinary audit service-lifecycle
records can share the same printk route, but this is not needed to establish
the terminal defect.

## Smallest secure correction

For the maintenance implementation pass, add an early boot console threshold
of **`loglevel=5`** to the image's kernel arguments and retain both console
devices. Linux prints only priorities numerically lower than the threshold;
this suppresses audit's `KERN_NOTICE` console path while retaining kernel
warning, error, critical, alert, and emergency messages. Do not use `quiet`,
disable auditing, disable SELinux, remove serial boot diagnostics, grant
`sl_platformd_t` write/`mac_admin`, or enable broad audit rate suppression.

The implementation must leave persistent journald audit capture enabled and
prove that the same records remain queryable after they are no longer printed
over the UI. A bootc/upstream improvement that avoids install-authority probes
for a genuinely read-only status operation would reduce audit noise at its
source and should be tracked separately. It is not a reason to expand the
0.0.3 security boundary. Periodic UI repaint could improve resilience, but it
is not a substitute for separating routine kernel notices from interactive
terminal output.

## Security implications

The proposed threshold changes console presentation, not SELinux enforcement,
audit generation, persistent audit storage, or D-Bus authorization. It avoids
turning expected negative probes into permissions. The tradeoff is that all
kernel `NOTICE` and `INFO` output, not only audit notices, will cease appearing
on the interactive consoles; those records remain in the journal. Warning and
higher-severity boot failures remain visible. Acceptance must verify these
claims on the built candidate rather than infer them from configuration alone.

## Regression acceptance criteria

A corrected candidate should pass one genuine-KVM/OVMF test using a disposable
overlay and both configured appliance terminals:

1. SELinux remains Enforcing and the immutable-root checks still pass.
2. `tty1` and `ttyS0` are still owned only by the two confined, unprivileged
   appliance-console instances; gettys remain masked.
3. The appliance UI is visibly rendered before the stimulus.
4. Repeated Session1 status calls and at least one normal `sl-remoted`
   reconciliation produce the known bootc audit events in persistent journald.
5. No audit record overwrites either visible appliance terminal after render.
6. A controlled kernel warning/error sentinel remains visible, proving that
   unrelated important boot diagnostics were not hidden.
7. Operator input still refreshes the UI and completes one harmless navigation
   action after the audit stimulus; serial transcript and a `tty1` QMP
   screenshot provide visible evidence.
8. Status calls succeed, no unexpected AVC class appears, system health remains
   good, the source disk is unchanged, and shutdown is clean.

## Recommendation and remaining unknowns

**GO** to a small Pass 2 implementation centered on `loglevel=5`, followed by
the regression above. Do not publish 0.0.3.1 until both terminal surfaces and
persistent audit retention pass. Remaining questions are limited to the exact
`tty1` framebuffer result and whether the selected Fedora kernel preserves the
expected warning-versus-notice cutoff throughout early boot; both are runtime
acceptance questions, not architectural blockers.
