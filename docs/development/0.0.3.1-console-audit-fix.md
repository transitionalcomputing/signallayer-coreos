# SignalLayer CoreOS 0.0.3.1 console/audit fix

- **Status:** Genuine-KVM regression completed; visible-console regression remains
- **Date:** 2026-10-19
- **Release-validation recommendation:** NO-GO

## Scope and implementation

This maintenance change addresses issue #27 by appending `loglevel=5` to the
existing qcow2 kernel arguments. Both `console=tty0` and
`console=ttyS0,115200n8` remain configured. The change does not use `quiet`,
disable audit or SELinux, modify D-Bus or SELinux policy, grant privileges, or
change the appliance-console services. Kernel warnings and higher-severity
messages remain eligible for console output; notice-level audit records remain
available to persistent journald without sharing the interactive terminal.

The maintained boot harness now has a focused `--console-audit` mode. Its guest
probe stimulates the known bootc audit path, records persistent audit evidence,
emits notice/warning/error kernel sentinels, captures the serial stream, and
requests four QMP framebuffer screenshots around the stimulus and harmless
operator input. The evaluator also retains system health, console confinement,
capability, policy-integrity, immutable-mount, and write-rejection checks.

## Pass 3 genuine-KVM result

One bounded run booted the existing candidate under genuine KVM with two vCPUs,
QEMU 10.2.2, and the installed OVMF templates. No image or disk was rebuilt.
The source qcow2 checksum was verified before the run and remained
`dab119ffb3d068bcd0947058b7bfd8f52ed5e8b87f208cdb5e81254cbd3df7c6`
after clean guest shutdown. Evidence is preserved on `slit-coreosdev-01` at:

```text
/home/coreos/signallayer-coreos-0.0.3.1-pass2/image/build/output/console-audit-6vqikqsc/
```

The machine evaluator reported 23/23 checks passing. Manual inspection required
by the acceptance contract found that result insufficient: the serial log and
both post-stimulus framebuffer captures contain
`kauditd_printk_skb: ... callbacks suppressed`. On `ttyS0`, these messages
appear after the appliance rendered (serial lines 374, 377, and 378). The
`tty1-after-audit.ppm` capture shows the callback-suppression message displacing
the selection prompt, and `tty1-sentinels.ppm` shows further suppression output.
Thus `loglevel=5` hides individual notice-level AVC records but does not isolate
the appliance consoles from audit rate-limit summaries.

Passed runtime criteria:

- effective `loglevel=5`, both console routes, and console threshold 5;
- SELinux Enforcing before and after the stimulus;
- expected bootc audit records retained by persistent journald;
- controlled warning/error sentinels visible and all sentinels journaled;
- Enter input delivered after the stimulus and the UI visibly repainted;
- confined, unprivileged console processes with no effective capabilities;
- unchanged D-Bus policies, healthy system, immutable mounts, and rejected
  root/`/usr` writes;
- clean shutdown and unchanged source disk.

Failed runtime criteria:

- audit-related kernel output did not remain off `ttyS0`;
- `tty1` did not remain undisplaced after the audit stimulus.

No security weakening or security-boundary regression was observed. The
failure is in console isolation, and the existing evaluator's
`audit_not_on_serial` check does not recognize the callback-suppression form.
No retry was run because this is product behavior rather than an infrastructure
or harness-execution fault.

The result is **NO-GO** for 0.0.3.1 release validation. A future implementation
pass must address the audit rate-limit summary path and extend the evaluator to
detect it, while preserving SELinux Enforcing, persistent audit collection, and
warning/error visibility. Issue #28 remains out of scope.
