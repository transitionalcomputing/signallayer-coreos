# SignalLayer CoreOS 0.0.4 milestone plan

**Status:** PHASE 0 RECONCILIATION PROPOSED — implementation requires human approval of the corrected architecture

**Milestone:** 0.0.4 — Podman Foundation

**Contract:** [0.0.4 Podman security and runtime contract](../contracts/0.0.4-podman-runtime.md)

## Objective

Deliver and validate a secure rootless Podman foundation that can bootstrap one
fixed minimal management container without interactive login, unrestricted host
authority or dependence on that container for CoreOS recovery.

This plan sequences future implementation. No phase described here is complete
or authorized merely because this document exists.

## Baseline and dependencies

### Verified input baseline

- SignalLayer CoreOS `v0.0.3` is published and formally closed.
- Validated runtime source:
  `a286544a670fb62f3b834217a7c4478a45cc1945`.
- Phase 5E acceptance: 75/75 PASS.
- Complete A -> B -> A lifecycle: 45/45 PASS under genuine KVM.
- Existing fixed update, reboot and rollback paths, SELinux policy, immutable
  root, local recovery and boot harnesses remain mandatory regression coverage.

### Planning dependencies

Implementation must not begin until:

1. the roadmap and Podman runtime contract are on `main`;
2. the reconciled machine-persistent identity and subordinate-map strategy is
   approved, including upgrades where proposed numeric IDs are occupied;
3. the system-service bootstrap experiment and user-Quadlet alternative have
   explicit KVM decision criteria;
4. native overlay, `pasta` and immutable-store experiments have stop conditions;
5. compatibility-epoch graphroots and the pre-Podman guard are approved;
6. the three-type SELinux model and expanded-policy review gate are approved;
7. the exact data-preserving recovery transaction is bounded; and
8. fixture image trust, persistent state and rollback rules are decided.

### External dependencies

- Fedora Podman, Quadlet, crun/conmon and container-selinux behavior;
- systemd user managers, lingering, cgroups v2 and generated units;
- `newuidmap`/`newgidmap` subordinate-ID helpers;
- supported rootless overlay and network helpers;
- OCI image registry/archive and containers/image verification policy; and
- native x86_64 KVM with OVMF for release acceptance.

Exact versions become release evidence. No dependency may silently fall back to
an untested implementation.

## Development principles

- Work in focused phases and preserve a reviewable commit at each accepted
  boundary.
- Run cheap source/static tests before any OCI or qcow2 build.
- Build one candidate per evidence-driven correction; do not rebuild merely to
  explore.
- Treat AVCs, namespace failures and runtime errors as evidence, not automatic
  permission requests.
- Never use `audit2allow`, `--privileged`, `label=disable`, host networking,
  broad host mounts or an exposed Podman socket as a shortcut.
- Keep the 0.0.4 management container minimal. General reconciliation and
  workload orchestration belong to 0.0.5 and 0.0.6.
- Preserve all 0.0.3 negative security tests and acceptance semantics.
- Stop for architectural review when required authority or persistent state
  exceeds the approved contract.

## Phase 0 — Contract reconciliation and measured dependency selection

### Purpose

Reconcile measured Fedora behavior with the security contract before runtime
accounts, policy or units enter an image.

### Work products

- pinned dependency inventory;
- locked machine-persistent `sl-management` strategy with collision-safe,
  persistent subordinate mappings; `sl-runtime` remains reserved;
- comparative system-service and isolated user-Quadlet bootstrap experiments;
- native-overlay, `pasta` and immutable-store hypotheses with stop conditions;
- compatibility-epoch graphroot and pre-Podman guard design;
- distinct SELinux process, container/rootfs and persistent-data label roles;
- explicit recovery transaction and state ownership matrix; and
- minimal fixture identity, trust and compatibility metadata.

Phase 0 is documentation and investigation only. Its proposed mechanisms are
not implementation authorization or runtime validation.

### Gate 0

Human review must approve the reconciled invariants, Phase 1 experiment bounds
and stop conditions. No design may require a Podman socket, rootful container,
second machine authority, broad host access or recovery dependent on Podman.
Unresolved bootstrap authority, identity persistence or graph compatibility
stops implementation.

## Phase 1 — Rootless runtime substrate and bootstrap selection

### Purpose

Use one non-product fixture to select a CoreOS-authoritative rootless bootstrap
and prove identity, namespace, storage, network and SELinux feasibility.

### Expected implementation scope

- pinned runtime dependencies and build assertions;
- root-owned idempotent provisioning for the machine-local locked identity and
  collision-free subordinate maps;
- root-owned pre-Podman compatibility guard and one experimental epoch graph;
- explicit root-owned environment/storage/network configuration;
- the system-service bootstrap candidate using `User=sl-management` and an
  exact Podman command;
- user Quadlet only as a separately measured alternative if its override paths
  can be denied;
- preliminary three-type SELinux policy and inspection helpers; and
- static/runtime evidence needed to choose or reject mechanisms.

### Tests before image build

- fresh, occupied-ID, overlap, malformed-map and interrupted-provisioning fixtures;
- exact system-service command/environment assertions;
- Quadlet generation only if testing the alternative;
- compatibility-epoch and pre-Podman refusal fixtures;
- SELinux compilation plus expanded-template queries;
- path ownership/mode/context and prohibited-feature assertions; and
- checks excluding sockets, privilege, broad mounts, unpinned images and silent
  network/storage fallback.

### Gate 1 — Genuine-KVM feasibility and selection

One attributable diagnostic must prove:

- identity/mappings remain stable without login and differing numeric mappings
  do not create immutable-image ownership dependencies;
- the selected bootstrap runs rootless under CoreOS authority and the identity
  cannot alter it or control privileged services;
- if user Quadlet is evaluated, higher-priority paths, drop-ins, transient units
  and user-bus control are denied;
- cgroups v2, user namespace, native overlay and explicit `pasta` match evidence;
- VFS/FUSE fallback, missing helpers and incompatible epoch metadata fail closed;
- the exact management SELinux transition works and same-MCS generic access is
  denied by type enforcement; and
- breaking the entire runtime leaves CoreOS Platform/console/recovery healthy.

Broad SELinux authority, rootful fallback, mutable bootstrap, unrestricted
same-UID control or incompatible graph access stops the phase for review.

## Phase 2 — Fixed Management Plane bootstrap fixture

### Purpose

Replace the Phase 1 test fixture with the digest-pinned minimal management
fixture using only mechanisms accepted at Gate 1.

### Expected implementation scope

- attributable minimal fixture artifact;
- exact digest in the CoreOS-bundled read-only
  `/usr/lib/containers/storage` additional store;
- selected root-owned bootstrap definition and fixed command;
- separate persistent config/data paths with policy-defined labels and no
  `:z`/`:Z` relabeling;
- bounded health, restart and start-limit behavior; and
- native status plus exact recovery actions approved at Gate 0.

The fixture has no orchestration, Podman socket, arbitrary desired state or
CoreOS mutation authority.

### Gate 2 — Bootstrap acceptance

- starts without login from an empty writable graph and retained digest while
  registry/network are unavailable;
- immutable store digest, hashes, ownership, xattrs and labels remain unchanged;
- rootless consumption works across accepted machine-local numeric mappings;
- missing, invalid and policy-rejected images fail boundedly without fallback;
- exact service/image/entrypoint/namespaces and listener inventory are recorded;
- persistent data survives restart/reboot with labels intact;
- bootstrap override, writable-store substitution and unrelated-user store
  access are denied; and
- no Podman socket or general runtime-control interface is reachable.

## Phase 3 — Confinement, failure and native recovery

### Purpose

Complete negative security coverage and prove CoreOS can recover when Podman,
the fixture or disposable graph metadata is failed or hostile.

### Expected implementation scope

- accepted dedicated process, container/rootfs and persistent-data types;
- resource limits and CoreOS storage reserve;
- CoreOS-owned compatibility guard and bounded recovery transaction;
- corruption/incompatibility detection without automatic destructive reset;
- machine-readable evidence and evaluator extensions.

### Gate 3 — Security and recovery acceptance

The KVM suite must deny host-root mapping, capability/setuid gain, host
filesystem/credential/journal access, Podman sockets, arbitrary workloads,
host namespaces/devices/listeners and command/systemd/policy control. Another
container with deliberately equal MCS must be denied persistent data by type
enforcement, with DAC arranged so it is not the deciding barrier.

Recovery must refuse active runtimes, symlinks, substituted mounts and wrong
epochs; survive interruption and full disk; atomically quarantine only the
verified graph; preserve application-data hashes, ownership, mounts and labels;
and work with Podman unavailable. Unexpected broad authority stops the phase;
policy is never broadened solely for the harness.

## Phase 4 — CoreOS lifecycle integration

### Purpose

Prove the Podman foundation and persistent state remain coherent across the
already accepted CoreOS deployment lifecycle.

### Gate 4 — A -> B -> A KVM lifecycle

Using fresh attributable 0.0.4 deployment artifacts and the existing fixed
Platform lifecycle:

1. boot deployment A and establish management/runtime persistent markers;
2. stage B through `corectl update`;
3. explicitly reboot into B;
4. verify exact B identity, management image identity and preserved state;
5. make the development registry unavailable;
6. select retained A through `corectl rollback`;
7. explicitly reboot into exact A; and
8. verify state, service health, enforcing SELinux, immutable mounts, negative
   boundaries and clean shutdown.

The source qcow2 remains unchanged. Each deployment must select only its
approved compatibility-epoch graphroot. Evidence must prove that older A never
opens or migrates incompatible B metadata, that the guard refuses before any
Podman command, and that application data remains unchanged. Refusal leaves
native recovery available; acceptance may not corrupt or silently reset state.

## Phase 5 — Release candidate and closure

### Purpose

Produce one final enforcing release candidate after all earlier gates are clean.

### Final acceptance package

- locked source/static tests and release build;
- package and configuration identity report;
- SELinux policy compile plus loaded-policy analysis;
- bootc lint and offline qcow2 inspection;
- one integrated genuine-KVM 0.0.4 acceptance run covering the complete
  contract matrix;
- one final genuine-KVM A -> B -> A lifecycle run;
- artifact checksums, OCI identities and source revision;
- concise provenance and known-limitations documentation; and
- confirmation that all VMs stopped and source artifacts remained unchanged.

No failed diagnostic, permissive run or superseded artifact can be represented
as final acceptance.

Gates 2–4 also require explicit evidence of stable persistent SELinux contexts
across restart and A→B→A, denial of unauthorized relabel, nondestructive
runtime-cache reconstruction from the matching `/usr` image store, and
first-boot activation through the selected bootstrap without login. Engine
metadata is disposable cache, not management application data; changing
container-store metadata cannot repair incompatible application schemas.

## Acceptance evidence model

Each gate preserves source/artifact identities, package/runtime versions,
resolved account and subordinate maps, selected epoch/graph identity, exact
bootstrap command, storage driver/mount program/backing filesystem, network
helper and reachability, process contexts/MCS/capabilities/seccomp, loaded-policy
queries, mounts/cgroups/listeners, image/store digests and metadata, persistent
data hashes/ownership/labels, recovery transaction state, AVC corpus, native
CoreOS health and VM/firmware/shutdown identity.

Evidence must distinguish CoreOS/system-service and user-Quadlet experiments.
The evaluator never infers missing evidence or treats post-run probe edits as
proof. A dry-run, displayed label, EROFS denial or absence of AVCs cannot alone
establish a security property.

## Release readiness criteria

SignalLayer CoreOS 0.0.4 is ready for release authorization only when:

1. the approved contract and implementation agree;
2. every required dependency and artifact is pinned and attributable;
3. the container is rootless, digest-pinned and confined, and its runtime
   identity cannot change bootstrap intent or exercise general Podman/host control;
4. native CoreOS remains healthy and recoverable with Podman absent, failed,
   corrupt or deliberately disabled;
5. immutable-store access, native overlay, epoch graph ownership, recovery,
   backup and rollback compatibility are proven without data loss;
6. missing/invalid images, network loss, crash loops and resource exhaustion
   fail according to contract;
7. no unexpected broad SELinux permission, Linux capability, host mount,
   device, namespace, socket or systemd authority exists;
8. the complete positive/negative KVM matrix passes under global Enforcing;
9. final A -> B -> A lifecycle acceptance passes or the approved compatibility
   failure behavior is demonstrated without data loss;
10. all applicable 0.0.3 regression checks remain green;
11. release documentation truthfully distinguishes implemented behavior,
    accepted limitations and deferred 0.0.5 work; and
12. no release blocker remains open.

## Explicit non-goals

This milestone does not implement:

- full Management Plane desired-state reconciliation;
- a general workload/runtime broker or public workload API;
- arbitrary application/container deployment;
- production product-role management;
- GPU or general device allocation;
- CloudOS, ServerOS, JumpOS or graphical desktop services;
- Kubernetes, VM or microVM backends;
- automatic CoreOS reboot/rollback; or
- the durable Management UI.

Any implementation that needs these capabilities has crossed the 0.0.4 release
boundary and must stop for a separately approved contract.

## Recommended implementation sequence

The required order is:

1. approve this plan and the runtime contract;
2. obtain human approval for reconciled identity, bootstrap, epoch-graph,
   SELinux, storage, network and recovery experiments;
3. select the rootless bootstrap and substrate through Gate 1 evidence;
4. add the fixed minimal management bootstrap;
5. prove negative confinement and data-preserving native recovery;
6. prove CoreOS update/rollback compatibility;
7. build one final candidate and run integrated release acceptance; and
8. prepare release documentation for separate authorization.

Do not parallelize later implementation across an unresolved security or state
boundary. A faster build is not useful if it fixes an authority model that has
not been approved.
