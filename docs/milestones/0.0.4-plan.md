# SignalLayer CoreOS 0.0.4 milestone plan

**Status:** ARCHITECTURALLY APPROVED — implementation remains gated by Phase 0 measurements and unresolved engineering decisions

**Milestone:** 0.0.4 — Podman Foundation

**Contract:** [0.0.4 Podman security and runtime contract](../contracts/0.0.4-podman-runtime.md)

## Objective

Deliver and validate a secure rootless Podman foundation that can bootstrap one
fixed minimal management container without interactive login, unrestricted host
authority or dependence on that container for CoreOS recovery.

This plan sequences future implementation. No phase described here is complete
or authorized merely because this document exists.

## Baseline and dependencies

### Verified input baseline

- SignalLayer CoreOS `v0.0.3` is published and formally closed.
- Validated runtime source:
  `a286544a670fb62f3b834217a7c4478a45cc1945`.
- Phase 5E acceptance: 75/75 PASS.
- Complete A -> B -> A lifecycle: 45/45 PASS under genuine KVM.
- Existing fixed update, reboot and rollback paths, SELinux policy, immutable
  root, local recovery and boot harnesses remain mandatory regression coverage.

### Planning dependencies

Implementation must not begin until:

1. the provisional [roadmap to 0.1.0](../roadmap/roadmap-to-0.1.0.md) is on
   `main`;
2. the Podman runtime contract is approved;
3. exact Fedora package availability and versions are captured from the pinned
   base without modifying it;
4. a fixed runtime UID/GID and subordinate ranges are reserved and checked for
   collision;
5. the rootless storage and network mechanisms are selected using the exact
   Fedora kernel, Podman and SELinux policy;
6. the initial management-image authenticity/delivery path is approved; and
7. the persistent-state and CoreOS rollback compatibility rule is decided.

### External dependencies

- Fedora Podman, Quadlet, crun/conmon and container-selinux behavior;
- systemd user managers, lingering, cgroups v2 and generated units;
- `newuidmap`/`newgidmap` subordinate-ID helpers;
- supported rootless overlay and network helpers;
- OCI image registry/archive and containers/image verification policy; and
- native x86_64 KVM with OVMF for release acceptance.

Exact versions become release evidence. No dependency may silently fall back to
an untested implementation.

## Development principles

- Work in focused phases and preserve a reviewable commit at each accepted
  boundary.
- Run cheap source/static tests before any OCI or qcow2 build.
- Build one candidate per evidence-driven correction; do not rebuild merely to
  explore.
- Treat AVCs, namespace failures and runtime errors as evidence, not automatic
  permission requests.
- Never use `audit2allow`, `--privileged`, `label=disable`, host networking,
  broad host mounts or an exposed Podman socket as a shortcut.
- Keep the 0.0.4 management container minimal. General reconciliation and
  workload orchestration belong to 0.0.5 and 0.0.6.
- Preserve all 0.0.3 negative security tests and acceptance semantics.
- Stop for architectural review when required authority or persistent state
  exceeds the approved contract.

## Phase 0 — Contract approval and measured dependency selection

### Purpose

Resolve the release-blocking design choices before runtime packages, accounts,
policy or units enter the image.

### Work products

- approved Podman runtime contract;
- package/runtime dependency inventory from the pinned Fedora base;
- fixed runtime UID/GID and subordinate-ID allocation record;
- selected storage driver and rootless network helper with rationale;
- selected trusted CoreOS-bundled `additionalimagestores` image layout under `/usr`, including verified rootless usability and provenance;
- state-path/ownership/SELinux matrix;
- user-manager bootstrap/linger design; and
- proposed minimal management fixture identity and compatibility metadata.

Phase 0 is strictly read-only investigation and version/feasibility recording; it must not modify implementation, SELinux, systemd, images or service state. Record the chosen `sl-management` identity (reserving `sl-runtime` for future workload execution), read-only CoreOS `/usr` image-store feasibility, and SELinux domain/type isolation feasibility before implementation authorization.

### Gate 0

- all twelve open decisions in the contract have an approved disposition or an
  explicitly bounded item deferred without affecting implementation;
- no design requires a Podman socket in the management container;
- no design creates a second host-root machine authority;
- recovery remains native and independent of Podman; and
- implementation file list and test plan are reviewed before code changes.

Failure to satisfy Gate 0 stops the milestone.

## Phase 1 — Rootless runtime substrate

### Purpose

Add only the packages, persistent identity, subordinate mappings, deterministic
storage configuration and SELinux/systemd foundations required to run a
rootless non-product test container.

### Expected implementation scope

- `Containerfile`: pinned runtime dependency installation and build assertions;
- dedicated `sl-management` fixed-account provisioning; `sl-runtime` is reserved for separate future workload control;
- deterministic subordinate UID/GID provisioning with collision failure;
- root-owned runtime home/config and explicit writable graph/cache directories;
- exact containers/storage/registries/policy defaults;
- image-owned per-UID Quadlet path and candidate declarative lingering via tmpfiles, with first-boot logind proof;
- minimal SELinux labels/interfaces required by the measured rootless path; and
- static/runtime inspection helpers used by maintained tests.

### Tests before image build

- package and configuration assertions;
- sysusers/account/subordinate-map fixture tests;
- Quadlet generator dry-run and generated-unit command assertions;
- SELinux module compilation and target-only policy queries;
- systemd unit verification;
- path ownership/mode/label assertions; and
- checks excluding rootful sockets, privileged flags, broad volumes, host
  namespaces and unpinned images.

### Gate 1 — Disposable rootless runtime KVM proof

A single genuine-KVM diagnostic candidate must prove:

- CoreOS boots normally with Podman idle;
- the persistent runtime user has no login, password, admin groups or
  capabilities;
- cgroups v2, subordinate maps, selected storage driver and rootless network
  helper match the approved design;
- a fixed non-product test container runs rootless in the expected SELinux
  domain/MCS categories with zero added capabilities;
- immutable host paths and unrelated persistent paths reject access; and
- stopping or breaking the runtime leaves native Platform/console/recovery
  healthy.

If the runtime requires broad SELinux access, rootful fallback, host networking,
generic device access or mutable bootstrap configuration, stop for review.

## Phase 2 — Fixed Management Plane bootstrap fixture

### Purpose

Replace the Phase 1 test container with the digest-pinned minimal management
fixture and prove automatic boot without introducing general orchestration.

### Expected implementation scope

- attributable minimal management container artifact;
- attributable immutable read-only `additionalimagestores` management image under `/usr`, with exact digest verified offline;
- image-owned rootless Quadlet with typed keys and fixed digest;
- systemd user-manager boot/linger integration;
- independent persistent management config/data directories with fixed policy-defined labels; no `:z`/`:Z` relabel or graph-owned named volumes;
- bounded health, startup, shutdown, restart and start-limit policy;
- native status sufficient to distinguish healthy, missing, invalid,
  crash-looping and disabled bootstrap; and
- fixed native reseed/retry/disable recovery operations if approved by Gate 0.

The fixture may expose a local health result. It must not accept general desired
state, create another container, receive a Podman socket or mutate CoreOS.

### Gate 2 — Bootstrap acceptance

- container starts after boot without any interactive login;
- exact image digest, config, entry point, generated service and namespaces are
  recorded;
- retained image starts with registry/network unavailable;
- missing, invalid and policy-rejected images fail boundedly while CoreOS reaches
  its operational target;
- crash restarts obey backoff/rate limits and do not loop forever;
- management durable state survives container restart and host reboot;
- mutable runtime identity cannot override image-owned Quadlet/user units; and
- no Podman socket or general runtime-control interface is reachable from the
  container.

## Phase 3 — Confinement, failure and native recovery

### Purpose

Complete negative security coverage and demonstrate that CoreOS can diagnose
and recover the runtime when every higher layer is failed or hostile.

### Expected implementation scope

- a dedicated management process domain and dedicated persistent-data file type, with narrowly scoped allow rules. Investigate Quadlet `SecurityLabelType=`/`SecurityLabelFileType=` and container-selinux templates as leading candidates, not frozen choices;
- resource limits/host reservation;
- native bounded diagnostic and exact recovery paths;
- corruption/incompatibility detection without destructive automatic reset;
- retained known-good management image selection metadata; and
- machine-readable acceptance/evaluator extensions.

### Gate 3 — Security and recovery acceptance

The genuine-KVM suite must prove positive behavior and deny:

- host-root mapping, capability gain and setuid escalation;
- host filesystem, bootc/OSTree, journal, credential and recovery-state access;
- rootful/rootless Podman socket use and arbitrary container creation;
- host PID/IPC/network namespace use, raw sockets, undeclared listeners and
  devices;
- other-container/volume access, including a deliberate equal-MCS probe proving type enforcement denies access even when MCS collides;
- arbitrary unit/command execution and policy loading; and
- CPU, memory, PID, storage or restart exhaustion that prevents native recovery.

It must also prove native inspection, disable, bounded retry and approved reseed
behavior while Podman and the management container are stopped or broken.

Unexpected AVCs or requested generic filesystem/device/systemd authority stop
the phase. Policy is never broadened solely to satisfy the harness.

## Phase 4 — CoreOS lifecycle integration

### Purpose

Prove the Podman foundation and persistent state remain coherent across the
already accepted CoreOS deployment lifecycle.

### Gate 4 — A -> B -> A KVM lifecycle

Using fresh attributable 0.0.4 deployment artifacts and the existing fixed
Platform lifecycle:

1. boot deployment A and establish management/runtime persistent markers;
2. stage B through `corectl update`;
3. explicitly reboot into B;
4. verify exact B identity, management image identity and preserved state;
5. make the development registry unavailable;
6. select retained A through `corectl rollback`;
7. explicitly reboot into exact A; and
8. verify state, service health, enforcing SELinux, immutable mounts, negative
   boundaries and clean shutdown.

The source qcow2 remains unchanged. If the older deployment cannot safely open
newer Podman state, the designed compatibility check must fail closed with
native recovery available; acceptance may not corrupt or silently reset state.

## Phase 5 — Release candidate and closure

### Purpose

Produce one final enforcing release candidate after all earlier gates are clean.

### Final acceptance package

- locked source/static tests and release build;
- package and configuration identity report;
- SELinux policy compile plus loaded-policy analysis;
- bootc lint and offline qcow2 inspection;
- one integrated genuine-KVM 0.0.4 acceptance run covering the complete
  contract matrix;
- one final genuine-KVM A -> B -> A lifecycle run;
- artifact checksums, OCI identities and source revision;
- concise provenance and known-limitations documentation; and
- confirmation that all VMs stopped and source artifacts remained unchanged.

No failed diagnostic, permissive run or superseded artifact can be represented
as final acceptance.

Gates 2–4 also require explicit evidence of stable persistent SELinux contexts across restarts and A->B->A, denial of unauthorized relabel, nondestructive runtime-cache reset and rehydration from the matching `/usr` image store, and first-boot user-manager activation without login. Engine metadata is disposable cache, not management application data; changing container store metadata cannot be assumed to fix incompatible application schemas.

## Acceptance evidence model

Each image/VM gate preserves:

- source commit and clean-tree status;
- exact OCI manifest/config IDs and qcow2 SHA-256;
- package/runtime/storage/network helper versions;
- generated Quadlet service and fixed command;
- account, UID/GID/subordinate maps and namespace maps;
- process SELinux context/MCS labels, capabilities, seccomp and NNP state;
- mounts, devices, cgroups, sockets/listeners and container inventory;
- systemd/unit/restart/health state;
- management image digest, trust-policy result and persistent-state identity;
- complete relevant AVC/audit corpus and loaded-policy query results;
- native CoreOS health, networking, immutable-root and Platform status;
- negative-probe outcomes with exact expected errno/policy denial where useful;
- boot IDs and deployment identities across lifecycle transitions; and
- QEMU/KVM/OVMF versions, exit result and shutdown disposition.

The evaluator must not infer missing evidence or accept post-run probe changes
as proof for a completed VM.

## Release readiness criteria

SignalLayer CoreOS 0.0.4 is ready for release authorization only when:

1. the approved contract and implementation agree;
2. every required dependency and artifact is pinned and attributable;
3. the management container is rootless, digest-pinned, confined and unable to
   control Podman or the host outside fixed bootstrap intent;
4. native CoreOS remains healthy and recoverable with Podman absent, failed,
   corrupt or deliberately disabled;
5. storage ownership, backup, cleanup and rollback compatibility are proven;
6. missing/invalid images, network loss, crash loops and resource exhaustion
   fail according to contract;
7. no unexpected broad SELinux permission, Linux capability, host mount,
   device, namespace, socket or systemd authority exists;
8. the complete positive/negative KVM matrix passes under global Enforcing;
9. final A -> B -> A lifecycle acceptance passes or the approved compatibility
   failure behavior is demonstrated without data loss;
10. all applicable 0.0.3 regression checks remain green;
11. release documentation truthfully distinguishes implemented behavior,
    accepted limitations and deferred 0.0.5 work; and
12. no release blocker remains open.

## Explicit non-goals

This milestone does not implement:

- full Management Plane desired-state reconciliation;
- a general workload/runtime broker or public workload API;
- arbitrary application/container deployment;
- production product-role management;
- GPU or general device allocation;
- CloudOS, ServerOS, JumpOS or graphical desktop services;
- Kubernetes, VM or microVM backends;
- automatic CoreOS reboot/rollback; or
- the durable Management UI.

Any implementation that needs these capabilities has crossed the 0.0.4 release
boundary and must stop for a separately approved contract.

## Recommended implementation sequence

The required order is:

1. approve this plan and the runtime contract;
2. resolve identity, sub-ID, storage, network, trust and rollback-compatibility
   decisions;
3. implement and validate the rootless runtime substrate;
4. add the fixed minimal management bootstrap;
5. prove negative confinement and native recovery;
6. prove CoreOS update/rollback compatibility;
7. build one final candidate and run integrated release acceptance; and
8. prepare release documentation for separate authorization.

Do not parallelize later implementation across an unresolved security or state
boundary. A faster build is not useful if it fixes an authority model that has
not been approved.
