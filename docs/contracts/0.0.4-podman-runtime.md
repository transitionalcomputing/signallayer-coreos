# SignalLayer CoreOS 0.0.4 Podman security and runtime contract

**Status:** PHASE 0 RECONCILIATION PROPOSED — corrected architecture requires human approval before implementation

**Release scope:** SignalLayer CoreOS 0.0.4

**Document class:** Architecture, security analysis and acceptance contract

## Purpose

This document defines the proposed Podman execution foundation for SignalLayer
CoreOS 0.0.4. It does not claim that Podman, Quadlet, a Management Plane
container, or the described policy exists in the current image.

The contract is subordinate to the published 0.0.3 platform boundary and the
[provisional roadmap](../roadmap/roadmap-to-0.1.0.md). CoreOS remains the
minimal immutable machine authority. The 0.0.3 Platform API, update staging,
explicit activation and retained-deployment rollback are inputs to this work;
0.0.4 must not reimplement them.

## Evidence classes

- **Verified baseline:** behavior demonstrated by the published 0.0.3 release.
- **Contract requirement:** behavior 0.0.4 must implement and validate after
  this draft receives approval.
- **Proposed mechanism:** a preferred implementation that remains replaceable
  until an implementation review confirms it.
- **Open decision:** a question that must be resolved before the affected code
  or policy is accepted.

## Current implementation findings

Repository inspection at the start of this design found:

- runtime Podman is not installed or configured by the CoreOS `Containerfile`;
- current Podman references are build-host tooling for OCI/qcow2 construction
  and test-policy analysis, not guest runtime capability;
- native services use fixed executables, systemd hardening, dedicated
  unprivileged identities where possible, exact D-Bus members and a maintained
  SELinux module;
- `sl-platformd` is the sole privileged machine-mutation authority and may
  control only specifically labeled fixed units;
- the maintained boot harness already collects serial, machine-readable,
  SELinux, immutable-root, systemd, networking and deployment evidence from
  disposable KVM/OVMF guests; and
- the 0.0.3 release has no general container runtime, Podman socket, workload
  API, runtime broker or Management Plane container.

## Authoritative upstream constraints

The design relies on these upstream properties, which must be rechecked against
the exact Fedora packages selected for the implementation candidate:

- Rootless Podman requires stable `/etc/subuid` and `/etc/subgid` mappings and
  stores images below `XDG_DATA_HOME` (or the user's home) while runtime data
  uses `XDG_RUNTIME_DIR`; see the
  [Podman rootless documentation](https://docs.podman.io/en/latest/markdown/podman.1.html#rootless-mode).
- Rootless Quadlet units must run in a user manager. Quadlet explicitly does not
  make a system unit rootless by adding `User=`, `Group=` or `DynamicUser=`;
  see [podman-systemd.unit](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html).
- Quadlet requires cgroups v2 and generates ordinary systemd services from
  administrator- or image-owned unit descriptions.
- A Podman API socket grants full Podman functionality and arbitrary code
  execution as the socket owner. It has no per-operation authorization layer;
  see [podman-system-service](https://docs.podman.io/en/stable/markdown/podman-system-service.1.html#security).
- Enabling systemd user lingering starts the user's manager at boot and keeps it
  available without an interactive login; see
  [loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html).
- `DynamicUser=` allocates an identity for the lifetime of a service, while
  rootless Podman requires stable subordinate-ID mappings and persistent engine
  ownership; see
  [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).
- Fedora's container SELinux policy separates container processes with
  `container_t` and MCS categories and defines container runtime/file types;
  see the maintained
  [container-selinux policy](https://github.com/containers/container-selinux/blob/main/container_selinux.8).
- Container image policy can reject by default and selectively admit signed
  identities; digest references verify content identity but do not alone prove
  publisher identity; see
  [containers-policy.json](https://github.com/containers/image/blob/main/docs/containers-policy.json.5.md).

These are constraints, not permission to copy upstream defaults without
testing them in the immutable bootc image and loaded Fedora SELinux policy.

## Target architecture

```text
                      native CoreOS recovery
                  console / diagnostics / rollback
                              |
                              v
+-------------------------------------------------------------------+
| SignalLayer CoreOS                                                |
|                                                                   |
|  sl-platformd        root-owned bootstrap/recovery policy         |
|  machine authority            |                                   |
|          |                     v                                   |
|          |       persistent sl-management identity                |
|          |                     |                                   |
|          |       CoreOS-owned system service (leading candidate)  |
|          |                     |                                   |
|          |             rootless Podman                             |
|          |                     |                                   |
|          |             minimal management container               |
|          |                                                         |
|          +---- narrow Platform API (no Podman API passthrough) ----+
+-------------------------------------------------------------------+
```

The rootless runtime is a platform capability, not a second machine authority.
CoreOS owns identity provisioning, the bootstrap definition, accepted image,
storage boundaries, recovery controls and evidence. The container owns only its
declared application state.

The leading bootstrap experiment is a root-owned systemd system service that
runs a fixed Podman command as `sl-management`. A rootless user manager and
Quadlet remain an alternative only if their same-UID override surfaces can be
isolated. Neither mechanism is selected until genuine-KVM comparison.

The minimal 0.0.4 container proves bootstrap and isolation; it does not
orchestrate workloads. The full Management Plane belongs to 0.0.5.

## Component responsibilities

| Component | Owns in 0.0.4 | Must not own |
| --- | --- | --- |
| CoreOS image | Runtime packages/configuration, identity provisioning, root-owned bootstrap definition, SELinux policy and recovery contract | Mutable Management Plane state or product-role policy |
| `sl-platformd` | Existing machine operations and separately approved exact observation | Podman CLI/API passthrough, arbitrary container specs or general workload lifecycle |
| system manager | Boot ordering and exact bootstrap supervision | Container business logic, arbitrary Podman commands or desired-state reconciliation |
| `sl-management` identity | One fixed rootless container invocation and explicit runtime/data paths | System-unit definition, privileged services, user-selected bootstrap overrides or general workloads |
| rootless Podman | Image/storage/network/user-namespace mechanics for the runtime identity | Host-root control, CoreOS deployment mutation or authorization policy |
| minimal management container | Fixed health/status fixture and explicitly mounted state | Workload orchestration, Podman socket, host filesystem, devices or Platform mutation |
| native recovery path | Disable/inspect/reconstruct exact runtime components while higher layers are unavailable | General shell or caller-selected Podman/systemd commands |

## Podman runtime contract

### Supported dependency set

The final implementation must pin and record the exact NEVRA or equivalent
package identity of every runtime dependency. The expected Fedora package
families are:

| Dependency | Requirement |
| --- | --- |
| `podman` | Required engine and Quadlet generator/client |
| `crun` | Preferred OCI runtime; exact default must be asserted, not assumed |
| `conmon` | Required container monitor when pulled by the selected Podman build |
| `containers-common` / containers libraries | Required configuration, image, storage and signature-policy support |
| `container-selinux` | Required enforcing container and runtime policy |
| `shadow-utils` helpers | Required `newuidmap`/`newgidmap` support for subordinate mappings |
| systemd | Required system/user manager, cgroups v2 placement and lifecycle |
| rootless network helper | Fedora-supported `pasta`/`passt` path selected after native validation |
| Netavark/Aardvark DNS | Include only if the selected rootless network contract requires them |
| `fuse-overlayfs` | Installed dependency that must not be selected automatically; use requires a separately reviewed contract amendment |

`runc`, `slirp4netns`, VFS storage, CNI and alternate OCI runtimes are not
simultaneously supported merely because packages are available. The
implementation review must select one supported combination, record the exact
versions and reject silent fallback to a weaker or untested path.

### Rootless execution

All 0.0.4 application containers run as the dedicated non-root runtime account.
Container UID 0 maps to the unprivileged host runtime UID, not host UID 0.
Additional container IDs map only through the account's explicit subordinate
UID/GID ranges.

Requirements:

- no rootful management container;
- no `--privileged`, host user namespace or host PID/IPC namespace;
- no setuid binaries added to the management image unless explicitly reviewed;
- no ambient host capabilities;
- no direct rootful or rootless Podman API socket inside the container;
- no mapping of host UID/GID 0 into the container namespace;
- no overlapping subordinate range with another managed identity; and
- mapping changes after persistent storage exists are prohibited without a
  migration design.

### Cgroups v2

The accepted environment must report a unified cgroups v2 hierarchy. The user
manager and generated container service must place the container in a
recognizable delegated subtree. CPU, memory, process and I/O limits must be
expressible through systemd/Podman configuration and visible in evidence.

CoreOS and recovery services must remain outside the runtime user's delegated
subtree. The runtime account cannot write arbitrary cgroup controllers or move
host processes. Resource exhaustion tests must reserve enough host capacity for
CoreOS status, console and recovery.

### Network namespaces

The default management container receives a private rootless network namespace.
Host networking is forbidden. In 0.0.4 it publishes no externally reachable
port unless a later approved contract identifies one exact endpoint and source
policy.

The selected rootless helper must be attributable and confined. DNS and egress
behavior must be explicit. Offline startup from a retained image must not wait
indefinitely for network readiness. A missing image may fail to start, but must
not block normal CoreOS boot.

### Seccomp and capabilities

The management container uses the supported Podman default seccomp profile as a
minimum and applies a reviewed narrower profile if its measured syscall set
makes that defensible. `seccomp=unconfined` is prohibited.

The initial container drops all Linux capabilities and adds none. It uses
`no-new-privileges`, a read-only root filesystem, private namespaces and
read-write tmpfs only for documented ephemeral paths. Any later capability is a
contract change requiring an exact need, negative tests and threat review.

The design must not use `Unmask=ALL`, broad `PodmanArgs=`, `label=disable`, host
devices, host `/proc`, host `/sys`, `/run`, `/etc`, `/usr`, `/boot`, `/sysroot`
or the host root as a volume.

### Storage driver

The target is native rootless overlay on local persistent storage. Phase 1
must positively prove the actual driver, native-overlay result, mount program,
backing filesystem, mounts and helper processes. VFS and automatic
`fuse-overlayfs` selection are stop conditions; leaving a helper unconfigured
is not proof that fallback cannot occur.

The selected compatibility-epoch graphroot must not reside on NFS or an
unsupported distributed filesystem. Startup fails before the container if the
driver, mount program, graphroot or compatibility epoch differs from the
CoreOS-owned selection. It must never silently initialize a second graphroot.

## Runtime identity model

### Decision: machine-persistent system identity

0.0.4 uses a locked system account named `sl-management`. Its numeric UID/GID
must remain stable for the lifetime of one machine's runtime state but need not
be identical across installations. `DynamicUser=` remains unsuitable because
Podman ownership and subordinate mappings persist. A global fixed number is
rejected: an upgraded 0.0.3 machine may already use it.

`sl-runtime` remains reserved for future workload infrastructure and must not
share the management account, mappings or store.

A root-owned, idempotent provisioner must run before Podman. It validates or
allocates the machine-local account and a collision-free, non-overlapping
subordinate UID/GID extent of at least 65,536 IDs; persists accepted values in
`/etc` and root-owned recovery metadata; and refuses partial, overlapping or
changed mappings once runtime state exists. Reboot, update, rollback and
recovery reuse the same values. Builder-local mappings are never target
reservations.

The account has locked credentials, a noninteractive shell, no administrative
groups or capabilities, and no authority to change its bootstrap service or
control privileged units. Every path derived from its numeric ID is resolved
after provisioning rather than embedded in immutable content.

## Management Plane bootstrap design

### Unresolved mechanism selection

A root-owned systemd **system** service is the leading Phase 1 experiment. It
uses `User=sl-management` and executes an exact CoreOS-owned rootless Podman
command. `User=` does not itself establish the required rootless environment;
Phase 1 must prove `HOME`, `XDG_RUNTIME_DIR`, graphroot/runroot, subordinate
maps, user namespace, cgroups v2 and SELinux transition without login.

Rootless user Quadlet is retained only as an alternative. Its higher-priority
writable generator paths, user-unit drop-ins, transient units and user bus make
a root-owned `/etc` symlink insufficient. It is acceptable only if loaded policy
and runtime tests prove that neither the container nor another same-UID process
can replace the generated unit or exercise user-manager control.

| Property | System-service candidate | User-Quadlet alternative |
| --- | --- | --- |
| Bootstrap definition | root-owned system unit | immutable Quadlet plus protected generator inputs |
| Rootless execution | fixed Podman command under `User=sl-management` | user manager invokes generated command |
| Login/linger | no interactive login; no linger assumed | declarative user-manager startup required |
| Principal risk | incomplete rootless environment/delegation | same-UID override and user-bus authority |
| Acceptance | genuine-KVM environment and confinement proof | all system candidate gates plus override denial |

Regardless of mechanism, the command fixes the manifest digest, `Pull=never`,
read-only rootfs, private namespaces, zero capabilities, NNP, exact mounts,
environment, entry point, health check, resources and deterministic name. There
is no shell, caller argument, unrestricted `PodmanArgs=` or Podman socket.

### Startup ordering

```text
local filesystems and persistent state mounts
        |
root-owned identity/subordinate-map provisioning
        |
root-owned compatibility guard selects epoch graphroot
        |
CoreOS-owned fixed rootless bootstrap
        |
bounded health observation
```

Normal `multi-user.target`, console, `sl-platformd` and recovery must not depend
on container success. Startup/shutdown deadlines, restart delay and start-rate
limits are bounded. Network is required only for a separately authorized image
retrieval action, not retained-image startup.

### Missing or invalid image

An absent, corrupt, rejected or incompatible image fails observably without tag
fallback, registry search or unpinned pull. CoreOS still reaches its operational
target; native status, console, update and rollback remain usable; known-good
state is retained; and only an exact authorized recovery flow may install a new
accepted digest.

## Runtime authorization boundary

### No Podman socket delegation

Neither `/run/podman/podman.sock` nor the runtime user's rootless Podman socket
is mounted into the Management Plane container. The Podman API is intentionally
not the Management Plane contract because socket possession grants arbitrary
code execution as the engine user and provides no operation-level policy.

The runtime socket is disabled unless a native component demonstrably needs
it. If enabled for implementation tooling, its filesystem and SELinux access
remain exclusive to the runtime identity and it is never network exposed.

### Broker decision

A narrow runtime broker is required **before** the Management Plane may create,
modify or remove general workloads. It is not implemented as part of the
minimal 0.0.4 bootstrap unless acceptance proves a fixed bootstrap operation
cannot be expressed safely through image-owned Quadlet/systemd state.

The future broker:

- runs without host root, normally as the runtime identity or a more narrowly
  separated identity;
- exposes typed workload operations, not Podman CLI flags or arbitrary OCI
  specifications;
- authenticates the Management Plane and authorizes each operation;
- validates image identity, mounts, namespaces, ports, devices, resources and
  labels against policy;
- owns no machine-level capability; and
- calls `sl-platformd` only through separately authorized Platform methods when
  a true machine operation is required.

`sl-platformd` must not become a Podman proxy. The broker must not become a
second privileged machine daemon. The exact broker process/API belongs to the
0.0.5 Management Plane contract.

In 0.0.4 the authorization boundary is deliberately closed: the minimal
container has no runtime-control interface, and the selected CoreOS-owned
bootstrap definition selects the only container and image it may run.

## SELinux and privilege model

### Required domains and labels

The design keeps three distinct label roles:

1. a dedicated management process domain;
2. a container root-filesystem/image file type used by Podman; and
3. a dedicated persistent management-data type.

Persistent data receives deterministic policy file contexts or a bounded
CoreOS-controlled initial labeling operation. Existing bind sources are not
labeled by `SecurityLabelFileType`; persistent mounts prohibit `:z` and `:Z`.
Generic `container_t` must be denied even when deliberately assigned the same
MCS categories, making type enforcement primary and MCS defense in depth.

Container-domain templates are experimental inputs, not least-privilege proof.
Phase 1 must inspect their expanded loaded-policy permissions and prove the
exact rootless transition, entrypoint access, type-request spoofing denial and
runtime/systemd/recovery access. If inherited permissions or runtime authority
exceed the contract, stop for architecture review.

Engine storage, bootstrap configuration, container rootfs, management data and
recovery metadata retain distinct types. No implementation may use
`label=disable`, permissive domains, container-loaded policy, enforcement
changes, generic `var_t`/`var_lib_t` access or blind `audit2allow` output.

### Host capability and filesystem boundary

The runtime account and container receive no host capabilities. `newuidmap` and
`newgidmap` are trusted only for the persisted subordinate mappings; their
identity and invocation are acceptance evidence.

The container receives no host device beyond minimal namespaced devices and no
host root, `/proc`, `/sys`, `/run`, `/etc`, `/usr`, `/boot`, `/sysroot`, bootc,
OSTree, credentials, journals, recovery metadata or runtime socket. It sees only
its read-only rootfs, tmpfs and exact typed application-data mount. A future
request for any broader host path or device is a contract change.

## Persistent-state model

| State | Proposed host location | Owner | Persistence/backup expectation |
| --- | --- | --- | --- |
| Root-owned bootstrap/runtime defaults | immutable `/usr` plus exact system unit, or approved protected Quadlet inputs | CoreOS/root | Replaced only by deployment |
| Runtime account and maps | `/etc/passwd`, `/etc/group`, `/etc/subuid`, `/etc/subgid` plus recovery record | CoreOS/root | Machine-persistent across deployments |
| Engine graph/writable layers | compatibility-epoch child under `/var/lib/sl-management/containers/` | `sl-management` | Reconstructible cache; never shared with incompatible epoch |
| Runtime cache/runroot | explicit paths resolved after identity provisioning | `sl-management` | Reconstructible/ephemeral |
| Immutable image store | `/usr/lib/containers/storage` | CoreOS/root | Read-only, deployment-versioned; rootless use requires proof |
| Management configuration/data | separate paths under `/var/lib/signallayer/management/` | field owner / management domain | Persistent, typed, versioned and backed up |
| Recovery metadata | `/var/lib/signallayer/runtime-recovery` | CoreOS/root | Minimal, interruption-safe, never container-writable |

A CoreOS-owned compatibility epoch selects the writable graphroot before any
Podman command can open or migrate it. The root-owned guard verifies epoch,
identity mappings, owner, mode, label and expected directory identity; mismatch
fails closed. Application-data schema compatibility is separate from Podman
metadata compatibility.

Reconstruction is explicit, offline and evidence-preserving. It inhibits the
exact service, proves no runtime process or mount is active, resolves bounded
paths without following untrusted symlinks, atomically quarantines only the
verified graphroot, records and fsyncs transaction state, and recreates only
graph/runroot. It never deletes quarantine automatically or mutates application
data. Recovery remains available with Podman and the Management Plane absent.

## Image trust and update model

### Identity and provenance

The bootstrap image reference is fully qualified and pinned to an OCI manifest
digest. The accepted manifest, config digest, source revision, build identity,
architecture, expected entry point and SBOM/provenance location are recorded in
release evidence.

Digest pinning proves content identity, not publisher identity. 0.0.4 must use
one of these approved trust paths:

1. a scoped, default-deny containers/image signature policy with a release
   trust root and exact repository identity; or
2. an image archive incorporated into and verified by the CoreOS release build,
   with network retrieval disabled at boot, until publisher-signature
   infrastructure is approved.

An unsigned network pull from a public tag is not acceptable for bootstrap.
The preferred 0.0.4 mechanism is an immutable, OS-bundled read-only `additionalimagestores` store under `/usr`; its construction and manifest digest must be verified by the CoreOS build/release chain. Validate rootless readability, ownership, SELinux, namespace mappings and store-format compatibility from the actual image. The CoreOS install/update provenance remains essential; image digest alone does not authenticate a publisher. A separate signed network image channel is deferred. If the proposed immutable store is infeasible, stop for a contract amendment rather than silently falling back.

### Retrieval and offline behavior

Normal boot uses only the locally retained accepted digest. Registry DNS,
credentials or availability cannot change the selected image. Retrieval is a
separate bounded operation with TLS verification, an allowlisted registry and
repository, fixed credentials source, size/storage limits, signature policy and
an immutable resulting digest.

Missing credentials, network failure, digest mismatch or verification failure
leaves the current known-good image and running container unchanged. Secrets
are never embedded in Quadlet, the OCI image, process arguments, logs or status.

### Management container lifecycle

0.0.4 installs one fixed initial management image and does not implement
general self-update or workload orchestration. Automatic Podman image updates
are disabled. A future update workflow must separate:

1. retrieve and verify candidate;
2. health-check without replacing known-good state;
3. select candidate;
4. bounded restart/activation;
5. accept or restore prior digest.

At least one known-good digest is retained until the candidate is accepted.
For 0.0.4, management image selection follows the versioned CoreOS deployment and rolls back with A->B->A. Independent management-image updates are deferred. Incompatible engine-cache metadata must fail closed and be safely reconstructible without deleting management data; incompatible application data schemas require a separate compatibility strategy.

## Failure and recovery model

| Failure | Required behavior | Recovery owner |
| --- | --- | --- |
| Management crash | Bounded restart/backoff; CoreOS remains healthy | system manager/native policy |
| Podman/runtime failure | No rootful, VFS, FUSE or unconfined fallback | CoreOS recovery |
| Missing/invalid image | `Pull=never` fails promptly; identity unchanged | exact recovery flow |
| Invalid bootstrap | Unit fails visibly; no mutable fallback | CoreOS image/recovery |
| Graph corruption | Preserve evidence; explicit transaction may quarantine exact graph | native recovery |
| Interrupted recovery/full disk | Resume or refuse safely; application data unchanged | native recovery |
| Epoch mismatch | Refuse before Podman opens graph; select only approved compatible graph | pre-Podman guard |
| Network/helper unavailable | Retained image behavior follows approved offline policy; no silent helper fallback | bootstrap/operator |
| Repeated failure | start limit holds failed; native recovery responsive | native status/console |
| CoreOS rollback | older deployment never opens incompatible newer graph | guard plus existing rollback |
| Management compromise | exact container/data boundary; disable and preserve evidence | native recovery |

Recovery never executes code from the failed management image and never depends
on Podman. Local console, `corectl`, `sl-platformd`, bootc rollback and native
diagnostics remain available with all container components stopped.

## Threat model

### Assumptions

- The kernel, systemd, SELinux policy, Podman/OCI runtime packages and immutable
  CoreOS image are trusted platform components.
- A pulled management image, its network inputs and any process inside it may be
  malicious.
- An attacker may control Management Plane data, induce crashes, exhaust
  resources, remove network access and attempt malformed runtime requests.
- Physical/pre-OS machine-owner access remains outside the 0.0.4 container
  boundary, consistent with the 0.0.3 Developer Preview limitations.

### Threat matrix

| Threat | Boundary/assumption | Preventive controls | Detection/evidence | Failure behavior | Residual risk |
| --- | --- | --- | --- | --- | --- |
| Container escape | Malicious container attacks kernel/runtime | Rootless user namespace, seccomp, zero caps, NNP, current pinned runtime, SELinux MCS, no devices/host namespaces | AVCs, audit, process context, namespace/capability evidence | Kill/fail container; native services remain | Kernel/runtime vulnerabilities can cross the boundary |
| Host privilege escalation | Container seeks host root | No UID 0 mapping, no privileged mode, no rootful socket, no setuid payload, no machine API mutation | UID maps, capabilities, socket/mount inventory, negative probes | Access denied; alert/preserve evidence | `newuidmap`/kernel/helper vulnerabilities remain trusted-code risk |
| Host filesystem access | Malicious image reads/writes host | Read-only image, exact private volumes, no host root/system mounts, SELinux private labels | Mountinfo, labels, write/read negative tests, AVCs | Deny without relabeling or broad grant | Data deliberately mounted remains exposed to container |
| SELinux bypass | Process attempts label escape or disable | Enforcing mode, `container_t` MCS, no label disable/permissive/SELinux fs access | Loaded-policy queries, contexts, unexpected AVC gate | Operation denied; candidate fails acceptance | Policy/runtime/kernel defects remain |
| Podman API abuse | Container tries to create arbitrary workloads | No socket mount, no network API, socket disabled/restricted | Socket inventory and connect-negative test | No runtime-control path | Compromise of native runtime user still controls its own Podman store |
| Malicious OCI image | Publisher/content is hostile | Digest pin, provenance, signature/default-deny policy or CoreOS-embedded archive, read-only root | Manifest/config/signature records and policy result | Reject before activation; keep known-good | Trusted publisher may ship vulnerable/malicious content |
| Unauthorized workload creation | Management code requests undeclared container | No 0.0.4 workload API; exact CoreOS-owned bootstrap; future typed broker | Container inventory must equal allowlist | Request impossible/denied | Runtime-user compromise can bypass future broker unless engine access is further separated |
| Credential exposure | Image/process reads registry or platform secrets | No embedded secrets/argv/env where avoidable; systemd credentials; exact mounts; redacted logs | Secret-path/mount/argv/log scans | Fail closed if credential unavailable | Container necessarily sees credentials explicitly delegated to it |
| Persistent-state tampering | Container alters bootstrap/engine/other state | Separate ownership/types; epoch guard; only private data mount writable | Ownership, labels, graph identity and application-data hashes | Refuse before Podman or quarantine exact graph; preserve data/evidence | Container can corrupt its own writable application data |
| Denial of service | CPU/memory/PIDs/disk/restart exhaustion | cgroup limits, quotas, log rate limits, start limits, reserved CoreOS resources | systemd/cgroup/storage metrics and failed state | Container stopped/degraded; CoreOS recovery remains responsive | Shared kernel/storage contention cannot be eliminated |
| Bootstrap compromise | Same-UID process attempts to replace startup intent | Root-owned system-service candidate, or user Quadlet only after all override paths are denied; fixed digest/command | Unit hash/ownership, user-bus and override-negative tests | Bootstrap rejected; no fallback | Root compromise remains outside boundary |
| Supply-chain compromise | Package/image/provenance source is altered | Pinned CoreOS base/packages/image digest, publisher verification, SBOM/provenance, reproducible evidence | Digest/signature/package inventory comparison | Reject candidate/release | Build infrastructure and trust-root compromise remain |

### Critical security concern for later milestones

All containers owned by one rootless Podman identity share that identity's
engine authority. A compromise of a component with direct engine access can
control every container in that store even though it is not host root. 0.0.4
avoids this by exposing no engine API to the minimal container. Before 0.0.5
adds workload mutation, the broker/identity design must decide whether one
runtime account is an acceptable fault domain or whether control and workload
execution require separate identities/stores.

## Acceptance test contract

All acceptance uses reviewed source, genuine x86_64 KVM/OVMF, disposable disk
overlays and preserved serial/QMP/journal/audit/policy evidence.

### Static, build and offline gates

- pinned dependency and configuration assertions;
- collision, overlap, partial-map and interrupted-provisioning fixtures;
- exact system-unit command assertions and, if retained, Quadlet generation;
- SELinux compile plus target and expanded-template policy queries;
- path ownership/mode/context and compatibility-epoch assertions;
- explicit checks excluding sockets, privilege, broad mounts, host namespaces,
  fallback drivers/helpers and unpinned images; and
- attributable source, OCI and qcow2 identities.

### Genuine-KVM acceptance matrix

| Area | Required positive proof | Required negative/failure proof |
| --- | --- | --- |
| Identity | machine-persistent UID/GID and stable subordinate maps | occupied proposed ID, overlap, partial map and mapping drift fail safely |
| Bootstrap | fixed root-owned service runs rootless without login | runtime identity cannot edit/control unit or privileged services |
| User-Quadlet alternative | protected generated unit starts without login | every higher-priority path, drop-in, transient unit and user-bus override denied |
| Rootless engine | expected namespaces/cgroups and zero capabilities | no rootful store/socket, host-root mapping or arbitrary workload |
| Immutable store | exact digest starts offline from an empty writable graph | unrelated user and writable shadow/tag cannot substitute image; store unchanged |
| Storage | native overlay with no mount program/helper | VFS/FUSE selection refuses startup |
| SELinux | exact management transition and typed data access | type spoofing and same-MCS generic container access denied with DAC permitting test |
| Networking | explicit `pasta`, expected egress/DNS and no listeners | host address/loopback reachability inventoried; helper/route/DNS failure bounded |
| State | selected epoch graph and separate application data | mismatch rejected before Podman; no cross-epoch graph open/migration |
| Recovery | exact graph reconstructed with data hashes/labels unchanged | symlink/mount race, active runtime, interruption and full disk fail safely |
| Native health | CoreOS services, console and Platform remain healthy | Podman/bootstrap absent, corrupt or disabled never blocks recovery |

A successful dry-run, process label, EROFS denial or absence of AVCs alone does
not prove the corresponding security property.

### CoreOS lifecycle compatibility gate

A genuine-KVM A→B→A cycle must prove exact deployment/image/epoch identities,
identity-map persistence, stable data contexts, no incompatible graph access,
non-destructive recovery and application-schema compatibility or explicit
pre-activation refusal. Podman failure never blocks console, `corectl`, update
or rollback. No test may relax an accepted 0.0.3 invariant.

## Explicit 0.0.4 release scope

### Required in 0.0.4

- pinned Podman and selected rootless dependencies;
- locked machine-persistent identity and stable collision-safe subordinate maps;
- one selected CoreOS-authoritative rootless bootstrap without login;
- one digest-pinned minimal management fixture without orchestration authority;
- native overlay, approved networking, cgroups v2 and confinement;
- separate epoch graph, persistent data and recovery authorities;
- offline known-good startup and bounded failures;
- native diagnostics and data-preserving recovery; and
- complete KVM security and A→B→A evidence.

### Deferred from 0.0.4

Full Management Plane APIs, general workload control, product roles, devices,
VM/microVM backends, graphical UI, multi-node operation, automatic OS rollback
and independent Management Plane self-update remain deferred. Fixtures are not
products or product roles.

## Open engineering decisions

The following require human disposition before implementation crosses them:

1. machine-local identity/subordinate-map provisioner and 0.0.3 upgrade behavior;
2. system-service bootstrap versus demonstrably isolated user Quadlet;
3. exact native-overlay and `pasta` guest behavior;
4. immutable-store construction and rootless identity-independent readability;
5. compatibility-epoch assignment, graphroot selection and pre-Podman guard;
6. three-type SELinux design and acceptable expanded template permissions;
7. exact data-preserving recovery transaction and resource reserve;
8. fixture image, health/compatibility protocol and trust path; and
9. separate runtime-control identity/store before later orchestration authority.

None may be resolved with a Podman socket, host root, broad filesystem/device
access, unconfined SELinux, arbitrary systemd/command control, `force_mask=shared`
or silent storage/network fallback.

## Additional mandatory acceptance probes

Test occupied UID 976 and differing mappings on two machines; all same-UID
bootstrap override paths; offline immutable-store start from an empty graph;
store hashes/ownership/xattrs/contexts before and after; native-overlay fallback
faults; exact host reachability with `pasta`; loaded-policy transition, spoofing
and equal-MCS denial; interrupted/symlink-substituted/full-disk recovery with
application-data sentinels; and A→B→A proof that neither deployment opens an
incompatible graphroot. Missing evidence is never inferred.

## Approval gate

This contract must be reviewed before implementation. Approval freezes the
security outcomes and release boundary, not every proposed path or package.
Implementation changes that alter authority, persistent state, image trust,
runtime identity, recovery ownership or the acceptance matrix require a focused
contract amendment before code changes continue.
