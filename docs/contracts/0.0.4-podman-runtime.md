# SignalLayer CoreOS 0.0.4 Podman security and runtime contract

**Status:** DRAFT — REQUIRES ARCHITECTURAL APPROVAL

**Release scope:** SignalLayer CoreOS 0.0.4

**Document class:** Architecture, security analysis and acceptance contract

## Purpose

This document defines the proposed Podman execution foundation for SignalLayer
CoreOS 0.0.4. It does not claim that Podman, Quadlet, a Management Plane
container, or the described policy exists in the current image.

The contract is subordinate to the published 0.0.3 platform boundary and the
[provisional roadmap](../roadmap/roadmap-to-0.1.0.md). CoreOS remains the
minimal immutable machine authority. The 0.0.3 Platform API, update staging,
explicit activation and retained-deployment rollback are inputs to this work;
0.0.4 must not reimplement them.

## Evidence classes

- **Verified baseline:** behavior demonstrated by the published 0.0.3 release.
- **Contract requirement:** behavior 0.0.4 must implement and validate after
  this draft receives approval.
- **Proposed mechanism:** a preferred implementation that remains replaceable
  until an implementation review confirms it.
- **Open decision:** a question that must be resolved before the affected code
  or policy is accepted.

## Current implementation findings

Repository inspection at the start of this design found:

- runtime Podman is not installed or configured by the CoreOS `Containerfile`;
- current Podman references are build-host tooling for OCI/qcow2 construction
  and test-policy analysis, not guest runtime capability;
- native services use fixed executables, systemd hardening, dedicated
  unprivileged identities where possible, exact D-Bus members and a maintained
  SELinux module;
- `sl-platformd` is the sole privileged machine-mutation authority and may
  control only specifically labeled fixed units;
- the maintained boot harness already collects serial, machine-readable,
  SELinux, immutable-root, systemd, networking and deployment evidence from
  disposable KVM/OVMF guests; and
- the 0.0.3 release has no general container runtime, Podman socket, workload
  API, runtime broker or Management Plane container.

## Authoritative upstream constraints

The design relies on these upstream properties, which must be rechecked against
the exact Fedora packages selected for the implementation candidate:

- Rootless Podman requires stable `/etc/subuid` and `/etc/subgid` mappings and
  stores images below `XDG_DATA_HOME` (or the user's home) while runtime data
  uses `XDG_RUNTIME_DIR`; see the
  [Podman rootless documentation](https://docs.podman.io/en/latest/markdown/podman.1.html#rootless-mode).
- Rootless Quadlet units must run in a user manager. Quadlet explicitly does not
  make a system unit rootless by adding `User=`, `Group=` or `DynamicUser=`;
  see [podman-systemd.unit](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html).
- Quadlet requires cgroups v2 and generates ordinary systemd services from
  administrator- or image-owned unit descriptions.
- A Podman API socket grants full Podman functionality and arbitrary code
  execution as the socket owner. It has no per-operation authorization layer;
  see [podman-system-service](https://docs.podman.io/en/stable/markdown/podman-system-service.1.html#security).
- Enabling systemd user lingering starts the user's manager at boot and keeps it
  available without an interactive login; see
  [loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html).
- `DynamicUser=` allocates an identity for the lifetime of a service, while
  rootless Podman requires stable subordinate-ID mappings and persistent engine
  ownership; see
  [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).
- Fedora's container SELinux policy separates container processes with
  `container_t` and MCS categories and defines container runtime/file types;
  see the maintained
  [container-selinux policy](https://github.com/containers/container-selinux/blob/main/container_selinux.8).
- Container image policy can reject by default and selectively admit signed
  identities; digest references verify content identity but do not alone prove
  publisher identity; see
  [containers-policy.json](https://github.com/containers/image/blob/main/docs/containers-policy.json.5.md).

These are constraints, not permission to copy upstream defaults without
testing them in the immutable bootc image and loaded Fedora SELinux policy.

## Target architecture

```text
                      native CoreOS recovery
                  console / diagnostics / rollback
                              |
                              v
+-------------------------------------------------------------------+
| SignalLayer CoreOS                                                |
|                                                                   |
|  sl-platformd        fixed bootstrap/recovery policy              |
|  machine authority            |                                   |
|          |                     v                                   |
|          |          persistent sl-runtime identity                |
|          |                     |                                   |
|          |             systemd user manager                       |
|          |                     |                                   |
|          |             rootless Podman/Quadlet                     |
|          |                     |                                   |
|          |             minimal management container               |
|          |                                                         |
|          +---- narrow Platform API (no Podman API passthrough) ----+
+-------------------------------------------------------------------+
```

The rootless runtime is a platform capability, not a second machine authority.
CoreOS owns the account, bootstrap description, accepted image identity,
storage boundaries, recovery controls and evidence. The container owns only its
declared application state.

The minimal management container in 0.0.4 proves bootstrap and isolation. It
does not orchestrate general workloads. The full Management Plane and its
desired-state APIs belong to 0.0.5.

## Component responsibilities

| Component | Owns in 0.0.4 | Must not own |
| --- | --- | --- |
| CoreOS image | Runtime packages/configuration, fixed identity definition, image-owned Quadlet, SELinux policy and recovery contract | Mutable Management Plane state or product-role policy |
| `sl-platformd` | Existing machine operations and any separately approved exact platform observation | Podman CLI/API passthrough, arbitrary container specs or general workload lifecycle |
| system manager | Boot ordering, persistent runtime user manager, bounded bootstrap supervision | Container business logic or desired-state reconciliation |
| `sl-management` user manager | Exact rootless Quadlet-generated unit and its cgroup | Machine services, rootful Podman or arbitrary system units |
| rootless Podman | Container image/storage/network/user-namespace mechanics for the runtime identity | Host-root control, CoreOS deployment mutation or authorization policy |
| minimal management container | Fixed health/status fixture and its explicitly mounted state | Workload orchestration, Podman socket, host filesystem, devices or Platform mutation |
| native recovery path | Disable/inspect/reset/reseed exact runtime components while higher layers are unavailable | General shell or caller-selected Podman/systemd commands |

## Podman runtime contract

### Supported dependency set

The final implementation must pin and record the exact NEVRA or equivalent
package identity of every runtime dependency. The expected Fedora package
families are:

| Dependency | Requirement |
| --- | --- |
| `podman` | Required engine and Quadlet generator/client |
| `crun` | Preferred OCI runtime; exact default must be asserted, not assumed |
| `conmon` | Required container monitor when pulled by the selected Podman build |
| `containers-common` / containers libraries | Required configuration, image, storage and signature-policy support |
| `container-selinux` | Required enforcing container and runtime policy |
| `shadow-utils` helpers | Required `newuidmap`/`newgidmap` support for subordinate mappings |
| systemd | Required system/user manager, cgroups v2 placement and lifecycle |
| rootless network helper | Fedora-supported `pasta`/`passt` path selected after native validation |
| Netavark/Aardvark DNS | Include only if the selected rootless network contract requires them |
| `fuse-overlayfs` | Conditional fallback only if native rootless overlay is not supported and validated |

`runc`, `slirp4netns`, VFS storage, CNI and alternate OCI runtimes are not
simultaneously supported merely because packages are available. The
implementation review must select one supported combination, record the exact
versions and reject silent fallback to a weaker or untested path.

### Rootless execution

All 0.0.4 application containers run as the dedicated non-root runtime account.
Container UID 0 maps to the unprivileged host runtime UID, not host UID 0.
Additional container IDs map only through the account's explicit subordinate
UID/GID ranges.

Requirements:

- no rootful management container;
- no `--privileged`, host user namespace or host PID/IPC namespace;
- no setuid binaries added to the management image unless explicitly reviewed;
- no ambient host capabilities;
- no direct rootful or rootless Podman API socket inside the container;
- no mapping of host UID/GID 0 into the container namespace;
- no overlapping subordinate range with another managed identity; and
- mapping changes after persistent storage exists are prohibited without a
  migration design.

### Cgroups v2

The accepted environment must report a unified cgroups v2 hierarchy. The user
manager and generated container service must place the container in a
recognizable delegated subtree. CPU, memory, process and I/O limits must be
expressible through systemd/Podman configuration and visible in evidence.

CoreOS and recovery services must remain outside the runtime user's delegated
subtree. The runtime account cannot write arbitrary cgroup controllers or move
host processes. Resource exhaustion tests must reserve enough host capacity for
CoreOS status, console and recovery.

### Network namespaces

The default management container receives a private rootless network namespace.
Host networking is forbidden. In 0.0.4 it publishes no externally reachable
port unless a later approved contract identifies one exact endpoint and source
policy.

The selected rootless helper must be attributable and confined. DNS and egress
behavior must be explicit. Offline startup from a retained image must not wait
indefinitely for network readiness. A missing image may fail to start, but must
not block normal CoreOS boot.

### Seccomp and capabilities

The management container uses the supported Podman default seccomp profile as a
minimum and applies a reviewed narrower profile if its measured syscall set
makes that defensible. `seccomp=unconfined` is prohibited.

The initial container drops all Linux capabilities and adds none. It uses
`no-new-privileges`, a read-only root filesystem, private namespaces and
read-write tmpfs only for documented ephemeral paths. Any later capability is a
contract change requiring an exact need, negative tests and threat review.

The design must not use `Unmask=ALL`, broad `PodmanArgs=`, `label=disable`, host
devices, host `/proc`, host `/sys`, `/run`, `/etc`, `/usr`, `/boot`, `/sysroot`
or the host root as a volume.

### Storage driver

The target is rootless overlay storage on local persistent storage. Native
overlay or `fuse-overlayfs` must be selected by evidence from the exact Fedora
kernel/Podman/SELinux combination. VFS is not an accepted production fallback
because of its space and performance behavior.

The graph root must not reside on NFS or an unsupported distributed filesystem.
Runtime startup fails explicitly if the configured driver changes or storage
cannot be opened. It must never silently initialize a second graph root.

## Runtime identity model

### Decision: persistent system identity

0.0.4 uses a persistent system account, provisionally named `sl-management`.
`DynamicUser=` is rejected for this role because:

- rootless Quadlet requires a real user manager and does not support making a
  system Quadlet rootless with `DynamicUser=`;
- Podman graph ownership and subordinate UID/GID maps must remain stable across
  restarts, CoreOS updates and rollback; and
- an ephemeral/recycled UID is incompatible with durable engine and management
  state without additional privileged remapping.

This dedicated management-bootstrap identity must not become the general workload authority. `sl-runtime` is reserved for a separate future workload execution identity/store, subject to the v0.0.5/0.0.6 authorization contract.

The account has:

- an implementation-approved fixed UID/GID from a reserved project range;
- locked credentials and `/usr/sbin/nologin` (or equivalent noninteractive
  shell);
- no administrative group membership;
- one non-overlapping subordinate UID range and GID range, at least large
  enough for the approved management image;
- no inheritable, permitted, effective or ambient Linux capabilities;
- no interactive session requirement; and
- a systemd user manager started at boot through the approved lingering/user
  manager mechanism.

The exact UID/GID and subordinate ranges are open decisions. They must be
reserved centrally, collision-checked at build and first boot, and remain
stable for the lifetime of persistent runtime state.

### Declarative lingering

The management user manager must start without login. The leading declarative mechanism is an image-owned tmpfiles rule to create `/var/lib/systemd/linger/sl-management`; first-boot logind ordering, reboot behavior and marker-loss recovery require measured proof. No imperative manual `loginctl enable-linger` step may be necessary. CoreOS boot and native recovery remain independent.

### Writable-home hazard

A conventional writable home would allow the runtime identity to alter
`~/.config/containers/systemd` or user units and override image-owned bootstrap
intent. Therefore:

- the passwd home and all user-unit/Quadlet search paths are root-owned and not
  writable by `sl-management`;
- the approved Quadlet is image-owned in a search path limited to the exact
  runtime UID;
- writable Podman graph, configuration state needed at runtime, container data
  and cache are separate explicit directories; and
- `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_RUNTIME_DIR` values are
  fixed and tested so Podman never falls back into an unintended location.

The implementation must prove that an unprivileged runtime process cannot add
or replace a unit that the user manager will load.

## Management Plane bootstrap design

### Quadlet decision

Quadlet is the preferred 0.0.4 integration because it generates a normal
systemd service while preserving Podman's rootless model and allowing an
image-owned declarative container definition. This decision is conditional on
native verification of the exact Fedora package versions and generated unit.

The Quadlet must specify, without an arbitrary pass-through:

- a fully qualified image reference pinned by manifest digest;
- `Pull=never` for normal boot so startup does not change identity or depend on
  a registry;
- read-only container root filesystem and explicit writable tmpfs/state mounts;
- private user, PID, IPC, UTS and network namespaces;
- zero added capabilities, no-new-privileges and enforcing SELinux labeling;
- exact volumes, environment, entry point, health command and resource limits;
  and
- a deterministic container/service name.

`PodmanArgs=` is prohibited unless a reviewed option has no typed Quadlet key;
any exception must be a fixed image-owned value with an assertion against the
generated service command.

### Startup ordering

The proposed order is:

```text
local filesystems and persistent state mounts
        |
runtime identity/subordinate-map validation
        |
user runtime directory and sl-runtime user manager
        |
Quadlet-generated fixed management container unit
        |
bounded health observation
```

Normal CoreOS `multi-user.target`, the local console, `sl-platformd` and
recovery paths must not require successful container startup. Network ordering
is required only for an explicitly authorized seed/retrieval operation, not for
offline startup of a retained image.

The generated service uses bounded startup/shutdown deadlines,
`Restart=on-failure`, a nonzero `RestartSec`, and systemd start-rate limits.
After the limit is reached it remains failed and observable; it does not spin
forever. An operator/native recovery action may retry the exact unit after the
underlying problem is corrected.

### Missing or invalid image

If the pinned image is absent, corrupt, rejected by policy or incompatible:

- the container unit fails with a structured/observable reason;
- no tag fallback, registry search or unpinned pull occurs;
- CoreOS reaches its normal operational target;
- native status, console, update and rollback remain usable;
- the last known-good image and state are not deleted; and
- only a fixed, authorized reseed/recovery flow may install another accepted
  digest.

## Runtime authorization boundary

### No Podman socket delegation

Neither `/run/podman/podman.sock` nor the runtime user's rootless Podman socket
is mounted into the Management Plane container. The Podman API is intentionally
not the Management Plane contract because socket possession grants arbitrary
code execution as the engine user and provides no operation-level policy.

The runtime socket is disabled unless a native component demonstrably needs
it. If enabled for implementation tooling, its filesystem and SELinux access
remain exclusive to the runtime identity and it is never network exposed.

### Broker decision

A narrow runtime broker is required **before** the Management Plane may create,
modify or remove general workloads. It is not implemented as part of the
minimal 0.0.4 bootstrap unless acceptance proves a fixed bootstrap operation
cannot be expressed safely through image-owned Quadlet/systemd state.

The future broker:

- runs without host root, normally as the runtime identity or a more narrowly
  separated identity;
- exposes typed workload operations, not Podman CLI flags or arbitrary OCI
  specifications;
- authenticates the Management Plane and authorizes each operation;
- validates image identity, mounts, namespaces, ports, devices, resources and
  labels against policy;
- owns no machine-level capability; and
- calls `sl-platformd` only through separately authorized Platform methods when
  a true machine operation is required.

`sl-platformd` must not become a Podman proxy. The broker must not become a
second privileged machine daemon. The exact broker process/API belongs to the
0.0.5 Management Plane contract.

In 0.0.4 the authorization boundary is deliberately closed: the minimal
container has no runtime-control interface, and immutable Quadlet plus native
bootstrap selects the only container and image it may run.

## SELinux and privilege model

### Required domains and labels

- Podman/OCI runtime processes use Fedora's supported container-runtime domains
  from `container-selinux`.
- Management runs in a dedicated confined SELinux process domain, not generic `container_t`, with narrowly controlled domain transition.
- Persistent management data uses a dedicated SELinux file type established through CoreOS-owned file contexts, accessible only by the management domain and explicitly authorized native recovery domains. Ordinary containers must be denied even at equal MCS levels.
- Podman's random MCS category allocation does not durably reserve a pair after a container stops; fixed MCS may add defense in depth but type enforcement is the primary barrier.
- Persistent mounts prohibit both `:z` and `:Z` automatic relabeling; original data labels must survive restart, recovery and rollback.
- Engine storage, root-owned bootstrap configuration, management data and
  recovery metadata have distinct ownership and labels appropriate to their
  access paths.
- Any SignalLayer policy additions name exact types, paths and peers and compile
  alongside the existing maintained module.

Leading candidate mechanisms are Quadlet `SecurityLabelType=` and `SecurityLabelFileType=` and container-selinux custom container-domain templates. Their availability, rootless transitions and loaded-policy effective access must be proven on exact Fedora packages. Merely changing a file label while remaining in generic `container_t` does not establish the claimed boundary. If a custom domain cannot be implemented without broad allowances, stop for architectural review.

No implementation may use `label=disable`, make a container/runtime domain
permissive, load policy from a container, change global enforcement, grant
generic `var_t`/`var_lib_t` access or accept blind `audit2allow` output.

### Host capability boundary

The runtime account and container receive no host capabilities. The
`newuidmap`/`newgidmap` helpers are trusted platform dependencies with only the
privilege needed to establish configured subordinate mappings. Their ownership,
mode/capabilities and invocation are acceptance evidence.

No device is passed through in 0.0.4 beyond the minimal devices created by the
OCI runtime. `/dev/kvm`, GPUs, block devices, raw network devices, TPMs and host
input devices are excluded.

### Filesystem boundary

The container sees only:

- its read-only image;
- private tmpfs for approved ephemeral paths;
- its exact management configuration/data mounts; and
- explicitly generated system metadata that has been reviewed as non-secret.

It cannot mount or read CoreOS deployment internals, bootc/OSTree state, host
credentials, Podman engine storage, another container's volume, `/home`, the
host root or system journals. Diagnostics cross a future bounded interface
rather than broad journal or filesystem mounts.

## Persistent-state model

The following conceptual layout is a contract boundary; exact path spelling is
confirmed during implementation review.

| State | Proposed host location | Owner | Persistence/backup expectation |
| --- | --- | --- | --- |
| Image-owned Quadlet and runtime defaults | `/usr/share/containers/systemd/users/<uid>/` and `/usr/share/containers/` | CoreOS image/root | Immutable; replaced only by CoreOS deployment |
| Runtime account and subordinate maps | `/etc/passwd`, `/etc/group`, `/etc/subuid`, `/etc/subgid` through supported provisioning | CoreOS machine configuration/root | Persistent across deployment change; backed up as machine configuration |
| Podman graph/container metadata and writable layers (reconstructible cache only) | `/var/lib/sl-management/containers/storage` | `sl-management` | Persistent; engine-managed; consistency required across update/rollback |
| Runtime cache | `/var/cache/sl-management` | `sl-management` | Reconstructable; safe to remove while runtime is stopped |
| Runtime/runroot state | `/run/user/<uid>` and explicit runroot | user manager/`sl-management` | Ephemeral; recreated every boot |
| Immutable management image store | `/usr/share/signallayer/management-image-store/` (candidate) | CoreOS image/root | Read-only `additionalimagestores`, OS-versioned/rolled back; exact format and rootless access require verification |
| Management configuration | `/var/lib/signallayer/management/config` | provisioner or future Management Plane per field ownership | Persistent, versioned, backed up |
| Management durable data | `/var/lib/signallayer/management/state` | management container through private labeled mount | Persistent, schema-versioned, backed up before migration |
| Runtime logs | system journal with rate/retention policy | journald | Operational evidence; no private ad hoc log directory by default |
| Recovery metadata | `/var/lib/signallayer/runtime-recovery` | native CoreOS/root | Persistent, minimal, never writable by container/runtime account |

### State rules

- Engine graph metadata and writable layers are reconstructible cache; durable management data/configuration must be explicit directories outside Podman's graph and named-volume lifecycle. A reset must be offline, explicitly scoped, evidence-preserving, and must never delete data; rehydration must use the bundled matching `/usr` image.
- Every directory has an owner, mode, SELinux type, quota expectation, backup
  classification and cleanup operation.
- Cleanup is offline/bounded and refuses to run while the affected container or
  engine state is active.
- CoreOS rollback must not launch an older Podman version against a newer,
  incompatible graph/database without an explicit compatibility result.
- Schema migrations are transactional or retain a recoverable pre-migration
  copy; 0.0.4 does not invent Management Plane database migrations.
- Persistent volume content is never stored in the immutable deployment or an
  ephemeral container writable layer.

## Image trust and update model

### Identity and provenance

The bootstrap image reference is fully qualified and pinned to an OCI manifest
digest. The accepted manifest, config digest, source revision, build identity,
architecture, expected entry point and SBOM/provenance location are recorded in
release evidence.

Digest pinning proves content identity, not publisher identity. 0.0.4 must use
one of these approved trust paths:

1. a scoped, default-deny containers/image signature policy with a release
   trust root and exact repository identity; or
2. an image archive incorporated into and verified by the CoreOS release build,
   with network retrieval disabled at boot, until publisher-signature
   infrastructure is approved.

An unsigned network pull from a public tag is not acceptable for bootstrap.
The preferred 0.0.4 mechanism is an immutable, OS-bundled read-only `additionalimagestores` store under `/usr`; its construction and manifest digest must be verified by the CoreOS build/release chain. Validate rootless readability, ownership, SELinux, namespace mappings and store-format compatibility from the actual image. The CoreOS install/update provenance remains essential; image digest alone does not authenticate a publisher. A separate signed network image channel is deferred. If the proposed immutable store is infeasible, stop for a contract amendment rather than silently falling back.

### Retrieval and offline behavior

Normal boot uses only the locally retained accepted digest. Registry DNS,
credentials or availability cannot change the selected image. Retrieval is a
separate bounded operation with TLS verification, an allowlisted registry and
repository, fixed credentials source, size/storage limits, signature policy and
an immutable resulting digest.

Missing credentials, network failure, digest mismatch or verification failure
leaves the current known-good image and running container unchanged. Secrets
are never embedded in Quadlet, the OCI image, process arguments, logs or status.

### Management container lifecycle

0.0.4 installs one fixed initial management image and does not implement
general self-update or workload orchestration. Automatic Podman image updates
are disabled. A future update workflow must separate:

1. retrieve and verify candidate;
2. health-check without replacing known-good state;
3. select candidate;
4. bounded restart/activation;
5. accept or restore prior digest.

At least one known-good digest is retained until the candidate is accepted.
For 0.0.4, management image selection follows the versioned CoreOS deployment and rolls back with A->B->A. Independent management-image updates are deferred. Incompatible engine-cache metadata must fail closed and be safely reconstructible without deleting management data; incompatible application data schemas require a separate compatibility strategy.

## Failure and recovery model

| Failure | Required behavior | Recovery owner |
| --- | --- | --- |
| Management process crash | Bounded restart/backoff; stop after rate limit; CoreOS remains healthy | User manager/native bootstrap policy |
| Podman/OCI runtime failure | Container fails; no fallback to rootful/unconfined runtime; native diagnostics remain | CoreOS operator/recovery |
| Missing image | `Pull=never` startup fails promptly; no tag fallback; CoreOS boot continues | Fixed reseed/recovery flow |
| Invalid Quadlet/config | Generator/unit failure is visible; last image/state retained; no arbitrary generated command | CoreOS image/update or root-owned override recovery |
| Engine storage corruption | Stop runtime, preserve evidence, refuse automatic destructive reset | Native recovery with explicit operator action |
| Network unavailable | Retained image starts offline; retrieval fails boundedly without replacing known-good | Retrieval worker/operator |
| Incompatible management version | Compatibility preflight rejects activation; prior accepted digest stays selected | Bootstrap/recovery policy |
| Repeated startup failure | systemd start limit holds unit failed; no boot blockage or infinite loop | Native status/console recovery |
| CoreOS update | Preserve state, revalidate runtime compatibility, keep prior deployment recoverable | Existing bootc/Platform lifecycle |
| CoreOS rollback | Start only if persistent engine/state schemas remain compatible; otherwise fail safely with recovery available | Existing rollback plus native runtime recovery |
| Management compromise | Attacker limited to container and declared mounts; revoke credentials/disable unit/preserve evidence | CoreOS native recovery |

Recovery never depends on executing code from the failed management image.
Local console, `corectl`, `sl-platformd`, bootc rollback and native diagnostics
must work with Podman and the user manager stopped.

## Threat model

### Assumptions

- The kernel, systemd, SELinux policy, Podman/OCI runtime packages and immutable
  CoreOS image are trusted platform components.
- A pulled management image, its network inputs and any process inside it may be
  malicious.
- An attacker may control Management Plane data, induce crashes, exhaust
  resources, remove network access and attempt malformed runtime requests.
- Physical/pre-OS machine-owner access remains outside the 0.0.4 container
  boundary, consistent with the 0.0.3 Developer Preview limitations.

### Threat matrix

| Threat | Boundary/assumption | Preventive controls | Detection/evidence | Failure behavior | Residual risk |
| --- | --- | --- | --- | --- | --- |
| Container escape | Malicious container attacks kernel/runtime | Rootless user namespace, seccomp, zero caps, NNP, current pinned runtime, SELinux MCS, no devices/host namespaces | AVCs, audit, process context, namespace/capability evidence | Kill/fail container; native services remain | Kernel/runtime vulnerabilities can cross the boundary |
| Host privilege escalation | Container seeks host root | No UID 0 mapping, no privileged mode, no rootful socket, no setuid payload, no machine API mutation | UID maps, capabilities, socket/mount inventory, negative probes | Access denied; alert/preserve evidence | `newuidmap`/kernel/helper vulnerabilities remain trusted-code risk |
| Host filesystem access | Malicious image reads/writes host | Read-only image, exact private volumes, no host root/system mounts, SELinux private labels | Mountinfo, labels, write/read negative tests, AVCs | Deny without relabeling or broad grant | Data deliberately mounted remains exposed to container |
| SELinux bypass | Process attempts label escape or disable | Enforcing mode, `container_t` MCS, no label disable/permissive/SELinux fs access | Loaded-policy queries, contexts, unexpected AVC gate | Operation denied; candidate fails acceptance | Policy/runtime/kernel defects remain |
| Podman API abuse | Container tries to create arbitrary workloads | No socket mount, no network API, socket disabled/restricted | Socket inventory and connect-negative test | No runtime-control path | Compromise of native runtime user still controls its own Podman store |
| Malicious OCI image | Publisher/content is hostile | Digest pin, provenance, signature/default-deny policy or CoreOS-embedded archive, read-only root | Manifest/config/signature records and policy result | Reject before activation; keep known-good | Trusted publisher may ship vulnerable/malicious content |
| Unauthorized workload creation | Management code requests undeclared container | No 0.0.4 workload API; immutable fixed Quadlet; future typed broker | Container inventory must equal allowlist | Request impossible/denied | Runtime-user compromise can bypass future broker unless engine access is further separated |
| Credential exposure | Image/process reads registry or platform secrets | No embedded secrets/argv/env where avoidable; systemd credentials; exact mounts; redacted logs | Secret-path/mount/argv/log scans | Fail closed if credential unavailable | Container necessarily sees credentials explicitly delegated to it |
| Persistent-state tampering | Container alters bootstrap/engine/other state | Separate ownership/types; root-owned home/config/recovery; only private data mount writable | Ownership, labels, inotify/audit where justified, integrity checks | Refuse incompatible/corrupt state; preserve evidence | Container can corrupt its own writable application data |
| Denial of service | CPU/memory/PIDs/disk/restart exhaustion | cgroup limits, quotas, log rate limits, start limits, reserved CoreOS resources | systemd/cgroup/storage metrics and failed state | Container stopped/degraded; CoreOS recovery remains responsive | Shared kernel/storage contention cannot be eliminated |
| Bootstrap compromise | Mutable user config replaces startup intent | Image-owned per-UID Quadlet, non-writable home/config, fixed digest/command, generated-unit assertions | Hash/path/ownership checks and generated unit capture | Bootstrap rejected; no fallback | Root compromise remains outside boundary |
| Supply-chain compromise | Package/image/provenance source is altered | Pinned CoreOS base/packages/image digest, publisher verification, SBOM/provenance, reproducible evidence | Digest/signature/package inventory comparison | Reject candidate/release | Build infrastructure and trust-root compromise remain |

### Critical security concern for later milestones

All containers owned by one rootless Podman identity share that identity's
engine authority. A compromise of a component with direct engine access can
control every container in that store even though it is not host root. 0.0.4
avoids this by exposing no engine API to the minimal container. Before 0.0.5
adds workload mutation, the broker/identity design must decide whether one
runtime account is an acceptable fault domain or whether control and workload
execution require separate identities/stores.

## Acceptance test contract

All release acceptance runs use a freshly built candidate from the reviewed
source, native x86_64 KVM acceleration and OVMF. Disposable overlays preserve
the source qcow2. Serial, QMP, journal, audit, policy and machine-readable guest
evidence are retained under ignored output paths.

### Static, build and offline gates

- locked workspace tests and release build pass;
- SELinux policy compiles against the pinned Fedora policy;
- Quadlet generator dry-run and systemd verification succeed for the exact
  image-owned file;
- generated service command contains only approved fixed arguments;
- package, OCI runtime, network helper, storage driver and policy versions are
  recorded;
- sysusers/subordinate-ID provisioning is deterministic and collision checked;
- OCI/bootc lint and existing qcow2 offline inspection pass;
- file contexts for runtime configuration/state are verified offline; and
- source, OCI and qcow2 identities are recorded before boot.

### Genuine-KVM acceptance matrix

| Area | Positive case | Required negative/failure case |
| --- | --- | --- |
| Native boot | systemd reaches operational target; networking and native platform services healthy | Podman and management unit stopped/failed do not block target, console or Platform status |
| Rootless engine | exact runtime user can run the fixed image | root/rootful store has no management container; other unprivileged user cannot inspect/control it |
| Identity | stable UID/GID and subordinate maps match contract | no overlap, host UID 0 mapping, login shell, password or admin group |
| User namespace | container UID 0 maps to `sl-management`; additional IDs stay in reserved range | mapping host root or an unmapped host identity is rejected |
| Cgroups v2 | generated unit is in expected delegated subtree with limits/accounting | container cannot move host processes or write unrelated cgroups; resource exhaustion preserves native control |
| Capabilities/seccomp | `NoNewPrivs=1`, zero effective/permitted/ambient caps and expected seccomp mode | capability gain, setuid escalation and a blocked syscall fail |
| SELinux | global Enforcing; runtime/container/state contexts and unique MCS labels match | host/other-volume access denied; no unexpected AVC; no permissive/label-disable path |
| Mounts/filesystem | only exact mounts; rootfs read-only; declared state writable | writes to `/`, `/usr`, `/etc`, `/boot`, `/sysroot`, host `/var` and recovery metadata fail without mutation |
| Runtime control | fixed Quadlet container starts/stops/restarts through exact unit | no Podman socket in container; connect to rootful/rootless socket and arbitrary container creation denied |
| Networking | private namespace and approved helper; expected bounded egress/health | no host network, undeclared listener, raw socket or arbitrary port publication |
| Bootstrap | starts without login from retained digest; exact generated unit/image/entry point | missing/invalid image fails boundedly, no tag pull, no essential-boot failure or infinite restart |
| Crash recovery | controlled crash restarts within policy and reaches health | repeated crash reaches start limit while native recovery stays usable |
| Persistent state | declared marker survives container restart and host reboot | ephemeral data disappears; engine reset/cleanup cannot silently remove management data |
| Offline behavior | retained image starts with registry unavailable | missing image plus unavailable registry remains failed without replacing identity |
| Compromise boundary | container cannot inspect bootc/OSTree, journals, host credentials or other service state | representative read/connect/ioctl/mount/pid/device attempts are denied |
| Recovery | native status can disable/inspect/retry/reseed exact runtime while container is failed | container cannot invoke recovery, bootc, arbitrary systemctl or policy loading |
| Existing regression | all applicable 0.0.3 Phase 5E invariants remain green | no weakened authorization, SELinux, immutable-root or failure checks are excluded |

### CoreOS lifecycle compatibility gate

The final release candidate must run an A -> B -> A CoreOS lifecycle under
genuine KVM using the existing fixed update/reboot/rollback path. It must prove:

- the source qcow2 is unchanged;
- runtime and management persistent state survive compatible deployment
  activation and exact rollback;
- each boot reports exact deployment and management image identities;
- the management container either starts successfully or fails with the
  contract's explicit compatibility result;
- Podman/Management Plane failure never blocks `corectl`, console, update or
  rollback; and
- SELinux, immutable mounts, native services and unauthorized-operation
  denials remain intact on every boot.

No test may make the container privileged, disable SELinux, grant a broad host
mount/socket or relax an accepted 0.0.3 invariant to obtain PASS.

## Explicit 0.0.4 release scope

### Required in 0.0.4

- pinned Podman and selected rootless OCI/storage/network dependencies;
- persistent non-login runtime identity and stable subordinate mappings;
- rootless systemd/Quadlet bootstrap without interactive login;
- one digest-pinned minimal management container with no orchestration role;
- cgroups v2, seccomp, capability, namespace, mount and SELinux confinement;
- explicit engine, management, runtime, log and recovery state ownership;
- offline known-good startup and safe missing/invalid-image failure;
- CoreOS-owned diagnostics, bounded restart and recovery behavior;
- positive and negative genuine-KVM acceptance; and
- compatibility with existing CoreOS update and rollback.

### Deferred from 0.0.4

- full Management Plane desired-state implementation and APIs;
- runtime broker implementation unless required solely for the fixed bootstrap;
- general workload create/update/remove operations;
- production application deployment or role management;
- CloudOS, ServerOS, JumpOS and product-specific services;
- GPU, general device assignment and VM/microVM backends;
- graphical desktop or durable Management UI;
- multi-node/fleet orchestration;
- automatic CoreOS reboot or health-triggered rollback; and
- general self-update of the Management Plane container.

Reference containers are test fixtures, not products or product roles.

## Open engineering decisions

The following block implementation until resolved in the 0.0.4 implementation
plan or an approved amendment:

1. exact Podman/crun/container-selinux/storage/network package versions from
   the pinned Fedora base;
2. fixed runtime UID/GID and collision-free subordinate UID/GID ranges;
3. supported rootless overlay path: native overlay or `fuse-overlayfs`;
4. selected rootless network helper and DNS behavior;
5. exact user-manager boot/linger provisioning mechanism in an immutable image;
6. exact image-owned per-UID Quadlet location and protected XDG environment;
7. management image delivery: signed scoped policy versus CoreOS-embedded
   verified archive for the first release;
8. storage schema/Podman database compatibility across CoreOS rollback;
9. root-owned recovery command/API and how it exposes only exact operations;
10. minimum management fixture image, health protocol and compatibility field;
11. resource limits and minimum host reservation for recovery; and
12. design of a separate runtime-control identity/store before 0.0.5 can grant orchestration authority; and
13. demonstrable feasibility of the management-specific process domain and file type, equal-MCS cross-container denials, and stable contexts across rollback.

None of these may be resolved by granting a Podman socket, host root, broad
filesystem access, unconfined SELinux execution or arbitrary command control to
the management container.

## Additional mandatory acceptance probes

Under genuine KVM and loaded enforcing SELinux policy, demonstrate approved management access to the dedicated persistent-data type, denial to another container deliberately assigned the same MCS categories, no unauthorized relabel, stable contexts after stop/restart/host reboot/A->B->A and engine-cache reconstruction, and independent native recovery. Confirm the immutable `/usr` image is usable offline by the intended rootless identity and the user manager starts on first boot without login. No tests may rely only on the policy source or theoretical MCS uniqueness.

## Approval gate

This contract must be reviewed before implementation. Approval freezes the
security outcomes and release boundary, not every proposed path or package.
Implementation changes that alter authority, persistent state, image trust,
runtime identity, recovery ownership or the acceptance matrix require a focused
contract amendment before code changes continue.
