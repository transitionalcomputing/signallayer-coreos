# SignalLayer CoreOS 0.0.4 Podman security and runtime contract

**Status:** PHASE 1 PASS 2 CONTRACT ADOPTED — D1–D7 approved; D4 strengthened fail-closed wording confirmed October 23, 2026; separate authorization required before implementation

**Release scope:** SignalLayer CoreOS 0.0.4

**Document class:** Architecture, security analysis and acceptance contract

## Purpose

This document defines the proposed Podman execution foundation for SignalLayer
CoreOS 0.0.4. It does not claim that Podman, Quadlet, a Management Plane
container, or the described policy exists in the current image.

The contract is subordinate to the published 0.0.3 platform boundary and the
[provisional roadmap](../roadmap/roadmap-to-0.1.0.md). CoreOS remains the
minimal immutable machine authority. The 0.0.3 Platform API, update staging,
explicit activation and retained-deployment rollback are inputs to this work;
0.0.4 must not reimplement them.

## Evidence classes

- **Verified baseline:** behavior demonstrated by the published 0.0.3 release
  or the accepted bounded Phase 1 Pass 1 experiment, with its exact artifact
  identity and limitations.
- **Approved decision:** D1–D7, including D4's strengthened fail-closed wording
  confirmed on October 23, 2026. These decisions constrain the contract but do
  not prove runtime feasibility or an implementation.
- **Contract requirement:** behavior 0.0.4 must implement and validate only
  under a separately authorized engineering gate.
- **Experimental candidate:** Candidate C or B as defined below. Neither is an
  accepted runtime mechanism until the applicable evidence matrix passes.
- **Unproven:** a property requiring implementation, genuine-KVM evidence or a
  product-owner decision. Missing evidence is never inferred from a nearby
  passing assertion.

## Current implementation findings

Repository inspection at the start of this design found:

- runtime Podman is not installed or configured by the CoreOS `Containerfile`;
- current Podman references are build-host tooling for OCI/qcow2 construction
  and test-policy analysis, not guest runtime capability;
- native services use fixed executables, systemd hardening, dedicated
  unprivileged identities where possible, exact D-Bus members and a maintained
  SELinux module;
- `sl-platformd` is the sole privileged machine-mutation authority and may
  control only specifically labeled fixed units;
- the maintained boot harness already collects serial, machine-readable,
  SELinux, immutable-root, systemd, networking and deployment evidence from
  disposable KVM/OVMF guests; and
- the 0.0.3 release has no general container runtime, Podman socket, workload
  API, runtime broker or Management Plane container; and
- the accepted Phase 1 Pass 1 experiment proved one fixed root-owned system
  service could supervise a rootless fixture across two boots with 37/37
  assertions, but immutable content selection, trusted reset, production
  SELinux, recovery and A→B→A remain unproven.

## Authoritative upstream constraints

The design relies on these upstream properties, which must be rechecked against
the exact Fedora packages selected for the implementation candidate:

- Rootless Podman requires stable `/etc/subuid` and `/etc/subgid` mappings and
  stores images below `XDG_DATA_HOME` (or the user's home) while runtime data
  uses `XDG_RUNTIME_DIR`; see the
  [Podman rootless documentation](https://docs.podman.io/en/latest/markdown/podman.1.html#rootless-mode).
- Rootless Quadlet units must run in a user manager. Quadlet explicitly does not
  make a system unit rootless by adding `User=`, `Group=` or `DynamicUser=`;
  see [podman-systemd.unit](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html).
- Quadlet requires cgroups v2 and generates ordinary systemd services, but
  Pass 2 does not select Quadlet or a systemd user manager.
- A Podman API socket grants full Podman functionality and arbitrary code
  execution as the socket owner. It has no per-operation authorization layer;
  see [podman-system-service](https://docs.podman.io/en/stable/markdown/podman-system-service.1.html#security).
- Enabling systemd user lingering starts the user's manager at boot and keeps it
  available without an interactive login; see
  [loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html).
- `DynamicUser=` allocates an identity for the lifetime of a service, while
  rootless Podman requires stable subordinate-ID mappings and persistent engine
  ownership; see
  [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).
- Fedora's container SELinux policy separates container processes with
  `container_t` and MCS categories and defines container runtime/file types;
  see the maintained
  [container-selinux policy](https://github.com/containers/container-selinux/blob/main/container_selinux.8).
- Container image policy can reject by default and selectively admit signed
  identities; digest references verify content identity but do not alone prove
  publisher identity; see
  [containers-policy.json](https://github.com/containers/image/blob/main/docs/containers-policy.json.5.md).

- `podman run --rootfs` treats the first argument as an externally managed
  exploded rootfs rather than an image. The optional `:O` form creates an
  overlay whose upper content is stored in container storage; Candidate C
  therefore forbids `:O` and must measure the actual Fedora 44 mounts.
- Rootless `storage.conf` and `containers.conf` under writable user configuration
  paths can override system configuration, and environment variables can select
  alternate configuration or storage. Merely inspecting resolved configuration
  after launch is not proof that trusted configuration was selected.
- `additionalimagestores` are documented as read-only inputs, but the primary
  graph remains writable and containers/storage metadata and precedence still
  require independent effective-content proof.

These are constraints, not permission to copy upstream defaults without
testing them in the immutable bootc image and loaded Fedora SELinux policy.

## Target architecture

```text
                         native CoreOS recovery
                     console / diagnostics / rollback
                                 |
             +-------------------+-------------------+
             |                                       |
             v                                       v
  sl-platformd (unchanged)            sl-management-reset.service
  fixed machine operations            root-owned lifecycle coordinator
                                             |
                                  fixed reset/launch executable
                                             |
                              sl-management-runtime.service
                              fixed delegated system service
                                             |
                            +----------------+----------------+
                            |                                 |
                  locked sl-management UID       sl-management-verify.service
                  one contained cgroup tree       root-owned confined verifier
                            |                                 |
                  rootless Podman invocation      independent content/process/
                      /               \           namespace/health evidence
         Candidate C (preferred)   Candidate B              |
         deployment rootfs         immutable OCI store       |
                                  + disposable graph         |
                      \               /                     |
                        minimal fixture <---------------------+
```

CoreOS owns identity provisioning, immutable bootstrap content, exact
configuration selection, reset/recovery, and evidence. The dedicated proposed
`sl-management-reset.service` and fixed
`/usr/libexec/signallayer/sl-management-reset` executable are the only reset
executor and launch coordinator. The unit is root-owned, has no public D-Bus
interface, accepts no caller-supplied operation or path, and is invoked only by
the approved root-owned systemd lifecycle. This contractual selection does not
authorize installing it.

**sl-platformd gains no new method, privilege, or authority from this contract.** It remains the sole existing machine-mutation API and does not
start arbitrary units, invoke Podman, or control the reset executor on behalf
of the Management Plane.

Candidate C invokes rootless Podman with `--rootfs` against one exact
deployment-owned rootfs and does not select executable content through an OCI
name, tag, image database or additional image store. Its Podman metadata,
runroot, conmon state and namespaces remain disposable and untrusted.

Candidate B remains a bounded comparison using a deployment-owned immutable
OCI store and a newly reconstructed writable graph. A digest or read-only store
does not neutralize writable-store precedence or metadata substitution.

Neither candidate is implemented or accepted. Candidate C does not establish
general OCI storage. The minimal fixture has no orchestration authority; the
Management Plane, runtime adapter and general workload lifecycle belong to
0.0.5.

## Podman runtime contract

### Supported dependency set

The final implementation must pin and record the exact NEVRA or equivalent
package identity of every runtime dependency. The expected Fedora package
families are:

| Dependency | Requirement |
| --- | --- |
| `podman` | Required engine/client; Quadlet is not selected for Pass 2 |
| `crun` | Preferred OCI runtime; exact default must be asserted, not assumed |
| `conmon` | Required container monitor when pulled by the selected Podman build |
| `containers-common` / containers libraries | Required configuration, image, storage and signature-policy support |
| `container-selinux` | Required enforcing container and runtime policy |
| `shadow-utils` helpers | Required `newuidmap`/`newgidmap` support for subordinate mappings |
| systemd | Required system manager, cgroups v2 placement and root-owned lifecycle; no user manager |
| rootless network helper | Fedora-supported `pasta`/`passt` path selected after native validation |
| Netavark/Aardvark DNS | Include only if the selected rootless network contract requires them |
| `fuse-overlayfs` | Installed dependency that must not be selected automatically; use requires a separately reviewed contract amendment |

`runc`, `slirp4netns`, VFS storage, CNI and alternate OCI runtimes are not
simultaneously supported merely because packages are available. The
implementation review must select one supported combination, record the exact
versions and reject silent fallback to a weaker or untested path.

### Rootless execution

All 0.0.4 application containers run as the dedicated non-root runtime account.
Container UID 0 maps to the unprivileged host runtime UID, not host UID 0.
Additional container IDs map only through the account's explicit subordinate
UID/GID ranges.

Requirements:

- no rootful management container;
- no `--privileged`, host user namespace or host PID/IPC namespace;
- no setuid binaries added to the fixture rootfs/image unless explicitly reviewed;
- no ambient host capabilities;
- no direct rootful or rootless Podman API socket inside the container;
- no mapping of host UID/GID 0 into the container namespace;
- no overlapping subordinate range with another managed identity; and
- mapping changes after persistent storage exists are prohibited without a
  migration design.

### Cgroups v2

The accepted environment must report a unified cgroups v2 hierarchy. The
system manager creates one recognizable delegated subtree for the fixed
`sl-management-runtime.service`; that unit uses
`Delegate=cpu cpuset io memory pids` and `KillMode=control-group`. No other
controller is delegated, and every Podman, conmon, helper and container process
must remain in that subtree. No user manager, Quadlet-generated service or
caller-generated unit participates in this design.

Fixed reviewed CPU, memory, PID and I/O limits are applied at the runtime-unit
boundary and must be visible in evidence. Exact non-default values are selected
and reviewed before implementation acceptance. Enforcement of separate
per-container limits remains experimental and **UNPROVEN** in 0.0.4; it is not
an accepted substitute for the unit-level boundary.

CoreOS and recovery services must remain outside the runtime user's delegated
subtree. The runtime account cannot write arbitrary cgroup controllers or move
host processes. Resource exhaustion tests must reserve enough host capacity for
CoreOS status, console and recovery.

### Network namespaces

The default management container receives a private rootless network namespace.
Host networking is forbidden. In 0.0.4 it publishes no externally reachable
port unless a later approved contract identifies one exact endpoint and source
policy.

The selected rootless helper must be attributable and confined. DNS and egress
behavior must be explicit. Offline startup from deployment-owned content must
not wait indefinitely for network readiness. Missing content may fail to start,
but must not block normal CoreOS boot.

### Seccomp and capabilities

The management container uses the supported Podman default seccomp profile as a
minimum and applies a reviewed narrower profile if its measured syscall set
makes that defensible. `seccomp=unconfined` is prohibited.

The initial container drops all Linux capabilities and adds none. It uses
`no-new-privileges`, a read-only root filesystem, private namespaces and
read-write tmpfs only for documented ephemeral paths. Any later capability is a
contract change requiring an exact need, negative tests and threat review.

The design must not use `Unmask=ALL`, broad `PodmanArgs=`, `label=disable`, host
devices, host `/proc`, host `/sys`, `/run`, `/etc`, `/usr`, `/boot`, `/sysroot`
or the host root as a volume. The only exception is Candidate C's exact rootfs
source defined below; it does not expose host `/usr` as a container volume.

### Storage and runtime state

The two candidates have different storage contracts and must not be forced
through one compatibility-epoch design.

Candidate C must use the exact deployment rootfs without the `:O` overlay form.
It must pass `--read-only` and independently prove that the effective root is a
read-only bind/mount of the approved deployment content with no writable upper
directory. Any Podman graphroot, runroot, database, lock, pause-process or
container metadata created by this invocation is disposable and cannot select
the rootfs, entrypoint, environment, user, working directory or mounts.

Candidate B must use the explicitly selected native rootless overlay driver,
an immutable deployment-owned image store and a newly reconstructed writable
graph/runroot. Copying or materializing trusted OCI layer content into any
runtime-UID-writable graph is unacceptable even when that graph is disposable;
trusted executable lower content must remain deployment-owned and immutable. VFS, `fuse-overlayfs`, alternate graphroot, automatic driver
selection and a persistent compatibility-epoch graph are prohibited for the
Pass 2 comparison. The experiment must establish whether Fedora 44 supports
the required rootless access, ownership and SELinux behavior. Unsupported
upstream behavior or any need for `force_mask=shared` is a stop condition.

For both candidates, CoreOS supplies one root-owned storage/configuration set
by an exact environment/path contract. The executor clears inherited variables
and fixes `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_RUNTIME_DIR`,
`CONTAINERS_STORAGE_CONF`, `CONTAINERS_CONF`, `CONTAINERS_CONF_OVERRIDE`,
`CONTAINERS_REGISTRIES_CONF`, `REGISTRY_AUTH_FILE`, `STORAGE_DRIVER`,
`STORAGE_OPTS`, `PATH`, `TMPDIR` and any selected policy path. It requires
`CONTAINER_HOST` and `CONTAINER_CONNECTION` to be absent. It rejects user files
under `$HOME/.config/containers`, `$XDG_CONFIG_HOME/containers`, per-user
`containers.conf.d`/`registries.conf.d`, `storage.conf`, `registries.conf`,
`policy.json`, `mounts.conf`, `auth.json`, Docker-compatible credential paths
and any other Fedora 44 Podman/containers search path discovered by measurement.

Root-side file-open evidence attributable to the launcher/Podman PID and start
time must prove which configuration files were consumed. Podman's own reported
resolved configuration is corroboration, not the authority. Unexpected config
opens or environment values fail before trust. The actual driver, graphroot,
runroot, mount program, helpers and opened files are evidence; silent fallback
is prohibited.

## Runtime identity model

### Decision: machine-persistent system identity

0.0.4 uses a locked system account named `sl-management`. Its numeric UID/GID
must remain stable for the lifetime of one machine's runtime state but need not
be identical across installations. `DynamicUser=` remains unsuitable because
Podman ownership and subordinate mappings persist. A global fixed number is
rejected: an upgraded 0.0.3 machine may already use it.

`sl-runtime` remains reserved for future workload infrastructure and must not
share the management account, mappings or store.

A root-owned, idempotent provisioner must run before Podman. It validates or
allocates the machine-local account and a collision-free, non-overlapping
subordinate UID/GID extent of at least 65,536 IDs; persists accepted values in
`/etc` and root-owned recovery metadata; and refuses partial, overlapping or
changed mappings once runtime state exists. Reboot, update, rollback and
recovery reuse the same values. Builder-local mappings are never target
reservations.

The account has locked credentials, a noninteractive shell, no administrative
groups or capabilities, and no authority to change its bootstrap service or
control privileged units. Every path derived from its numeric ID is resolved
after provisioning rather than embedded in immutable content.

## Management Plane bootstrap design

### Fixed reset executor and candidate launch

The proposed root-owned `sl-management-reset.service` executes only
`/usr/libexec/signallayer/sl-management-reset` with no arguments. It is the
single coordinator for teardown, quarantine, trusted configuration, candidate
selection, rootless launch, independent content verification and health
observation. It has no D-Bus service, socket or public CLI and is invoked only
through its fixed systemd dependencies/restart lifecycle. The Management Plane
and runtime UID cannot start, stop or parameterize it.

The executor starts exactly `sl-management-runtime.service`. This fixed system
service is the sole permitted `User=sl-management` system unit. It has no
`[Install]` section, is wanted by no target, uses `Restart=no`, has no socket,
path or timer activation unit, accepts no caller-controlled input and exposes
no public control interface. Only the coordinator's current transaction-bound
systemd job may start it; a root-owned pre-start guard validates the matching
transaction descriptor before `ExecStart`.

The runtime unit executes one fixed Podman command as `sl-management`. It uses
`Delegate=cpu cpuset io memory pids`, `KillMode=control-group` and
`FileDescriptorStoreMax=0`; its cgroup must be empty before start, and it
receives no inherited or socket-passed file descriptors. The fixed Podman
command passes `--security-opt=no-new-privileges` as a container execution
option; this is not a unit-level `NoNewPrivileges=` requirement because that
could interfere with setuid subordinate-ID mapping helpers. It also supplies
private namespaces, zero capabilities, a read-only root, exact tmpfs/data mounts,
entrypoint, argv, working directory, user, unit-level resources, networking
and deterministic name. It clears the inherited environment and establishes
the complete root-owned configuration contract before Podman. Unit or launch
failure returns the coordinator to state 1 and cannot trigger automatic
restart.

For Candidate C, the source is exactly
`/usr/lib/signallayer/management-rootfs` in the booted deployment. Resolution
must remain beneath that directory without symlink or mount escape. Podman uses
`--rootfs` without `:O`; CoreOS supplies all OCI-equivalent process settings.
The rootfs is root-owned, deployment-immutable, manifested, free of unexpected
devices/sockets/FIFOs and correctly labeled.

For Candidate B, the executor selects one deployment-owned immutable OCI store
and recorded manifest/config identity only after rebuilding empty disposable
metadata. It never pulls or resolves trusted content from the writable graph.
Trusted layers may not be copied/materialized into runtime-UID-writable storage.

### Runtime identity, subordinate-map and namespace coverage

Trusted reset accounts for more than processes whose host UID equals
`sl-management`. The root verifier builds an attributable resource set from the
fixed bootstrap InvocationID and cgroup ancestry, process parentage, user/group
ID maps, namespace inode relationships, mount ownership and recorded runtime
paths. It includes:

- every process running as the primary runtime UID;
- attributable processes/resources using the account's subordinate UID/GID
  mappings;
- Podman pause, conmon, OCI runtime and network/storage helper processes even
  when they run as root or another host identity;
- every process holding a relevant user, mount, PID, IPC or network namespace;
  and
- mounts, IPC objects, handles, sockets and keyrings capable of preserving or
  reintroducing bootstrap-controlled state.

Root uses `/proc/key-users` as the concrete per-UID keyring inventory basis,
including the primary and subordinate UID ranges, and correlates those counts
with audit evidence for relevant keyring operations. Missing visibility,
unattributable counts or unsupported kernel semantics fail closed rather than
being treated as an empty inventory.

Numeric membership in a subordinate range is never sufficient authority to
kill or alter a host object. The verifier correlates at least cgroup/ancestry,
namespace relationships, UID/GID maps and resource ownership. An object with
unexpected ownership or ambiguous attribution is preserved as evidence and
causes a bounded fail-closed reset; it is not cleaned indiscriminately.
Persistent application data is never cleaned. Negative fixtures must leave
attributable subordinate-mapped processes, namespace holders, mounts and IPC
objects, plus unrelated overlapping host identities, and prove both fail-closed
behavior and absence of collateral cleanup.

### Continuous process-creation exclusion and atomic lifecycle

Trusted reset closes every independent mechanism that could create a process as
`sl-management` or inside its bootstrap containment: the account is locked and
noninteractive; login, SSH, `su`/sudo/polkit delegation, lingering,
`user@<uid>.service`, the user manager/bus, user units/timers, cron/at jobs,
socket/D-Bus activation, unprivileged transient-unit creation and every other
system unit with `User=sl-management` are prohibited. Immutable unit/policy
configuration plus static, loaded-system and live D-Bus authorization
inventories must prove that the fixed root lifecycle is the only spawn source.
The Management Plane and runtime UID have no system-manager operation capable
of creating a process or unit. These are permanent spawn-path prohibitions;
they remain enforced before, during and after every reset transaction and are
never re-enabled when a transaction finishes.

The system manager places the authorized rootless runtime and all descendants
in one fixed cgroup-v2 subtree. The root coordinator holds a root-only lifecycle
lock and root-enforced activation inhibit continuously from state 1 through the
state-10 decision. This temporary transaction inhibit permits only the
coordinator's exact transaction-bound runtime start job and its fixed verifier
dependency; it does not implement or replace the permanent prohibitions above.
The lock coordinates only trusted reset and verification actors and is not
itself treated as process-exclusion evidence. No untrusted actor can release
the inhibit or create a transient replacement.

During teardown the executor inventories shared temporary locations,
POSIX/System V IPC, message queues, sockets, keyrings, namespace handles and
unexpected files outside approved disposable/application-data locations. It
uses cgroup kill plus pidfds where available to terminate and reap the complete
attributable subtree and independently finds processes or holders outside that
subtree through ancestry, maps and namespace relationships. It reaches a
zero-authorized-process/zero-relevant-holder fixed point and repeats those
checks immediately before launch.

Atomicity means that no attacker-controlled process or attributable resource
may enter or remain in the trusted launch environment between successful
cleanup and state 10. With alternate spawn routes still disabled, systemd
synchronously starts only the fixed runtime unit in the empty contained subtree.
The coordinator and verifier continuously reject cgroup membership, process,
namespace or resource events outside the expected transition set through
launch, content verification, health observation and trusted-state publication.
They monitor process creation with the proc connector or an equivalently
complete kernel process-event source, cgroup membership and `cgroup.events`,
and audit syscall evidence for IPC, keyring and namespace creation or use.
Each source must have a planted positive control in the same acceptance run;
any coverage gap makes the candidate **BLOCKED**. These monitors are defense in
depth: atomicity is established by the absence of both an unauthorized process
and an available spawn source, not by eventually observing a hostile process.
A process spawned during cleanup, or appearing after the final scan but before
or during launch, invalidates the transaction and triggers contained teardown;
it can never become part of a trusted result.

Authorized post-launch processes must derive from the current runtime unit
InvocationID, exact cgroup/ancestry and expected executable/SELinux-domain set;
helpers are additionally matched to reviewed parentage, maps and namespaces.
The root verifier and reset coordinator are trusted native actors outside the
runtime subtree. Any independent spawn surface that Fedora 44 cannot disable or
prove absent, any containment escape, or any ambiguous survivor/resource makes
the architecture **BLOCKED**. The experiment must not weaken this guarantee.

### Trusted-reset state machine and verifier authority

| State | Required transition and evidence | Executor |
| --- | --- | --- |
| 1. Inhibited | Acquire root lifecycle lock and transaction inhibit; stop runtime and verifier; begin a new root-owned transaction; permit only its exact runtime job and fixed verifier dependency | reset unit + system manager |
| 2. Spawn surface closed | Prove the immutable permanent prohibitions on login, linger, user manager, timers, schedulers, activation, transient-unit authority and every other bootstrap spawn path | reset unit + system manager |
| 3. Teardown verified | Cgroup-kill/reap attributable primary/subordinate/helper processes; independently prove zero relevant process/namespace/mount/resource holders | reset unit + verifier primitives |
| 4. Disposable state isolated | Inventory IPC/keyrings/temp/unexpected files; resolve exact paths; quarantine graph/runroot/database/locks; preserve ambiguous evidence and application data | reset unit |
| 5. Configuration established | Recreate exact state under root-owned parents; select immutable configuration; reject user overrides; record root-side opens | reset unit |
| 6. Deployment content selected | Select current rootfs/manifest for C or immutable store/identity for B; reject mutable/wrong deployment | reset unit |
| 7. Preconditions verified | Validate maps, cgroups, SELinux, storage/network, mounts/resources and transaction metadata; repeat zero-survivor/holder check | reset unit |
| 8. Fixed launch and verifier binding | With exclusion still enforced, synchronously start `sl-management-runtime.service` in its empty cgroup; validate the transaction descriptor before `ExecStart`; bind InvocationID/cgroup/maps/namespaces to the transaction; the runtime unit pulls `sl-management-verify.service` into the same transaction with `Wants=` and orders it with `Before=` while the verifier declares `After=` | reset unit + system manager |
| 9. Content and health verified | Root verifier independently measures effective content, config opens, process/resource containment and bounded health; it returns a transaction-scoped result but cannot publish trust; exclusion remains active | verify unit + reset unit |
| 10. Operational or failed | Reset coordinator publishes trusted-operational only for a fresh matching successful verifier result; otherwise contained teardown/quarantine and explicit failure; only now is the transaction inhibit released, while permanent spawn-path prohibitions remain enforced | reset unit + system manager |

State 10 is the sole trusted-operational transition. A cgroup-empty result,
service restart, verifier exit or health result alone cannot skip states.
Interruption/power loss is recorded in root-owned fsynced transaction metadata;
every boot quarantines incomplete disposable state as needed and restarts at
state 1. Resume from an intermediate state is forbidden. It never uses stale
namespaces or prior mutable content.

The exact proposed verifier is `sl-management-verify.service`, a root-owned
`Type=oneshot` unit running as root in the named confined
`sl_management_verify_t` domain. `sl-management-runtime.service` pulls it into
the authorized transaction using `Wants=sl-management-verify.service` and
`Before=sl-management-verify.service`; the verifier declares
`After=sl-management-runtime.service`. It has `RefuseManualStart=yes`, which
blocks explicit manual/D-Bus starts but not dependency activation from the
authorized root transaction. Because a root dependency could otherwise pull
it in, the root-owned transaction descriptor is the actual authorization
guard. The system manager tears it down with the reset transaction. A
root-owned, SELinux-confined transaction descriptor binds boot ID, reset
InvocationID, runtime InvocationID, cgroup identity, deployment/content identity and freshness. Missing, stale or
mismatched descriptors fail before inspection. The verifier accepts no caller
arguments or mutable paths, has read/inspect authority only for the fixed
runtime/evidence surfaces, and cannot launch, stop, repair or mark the fixture
trusted. It writes only a transaction-scoped result for the reset coordinator.

Independent activation, verifier failure/interruption or a result from another
transaction cannot advance state 9 or 10. The Management Plane cannot invoke or
alter either unit. **sl-platformd gains no new method, privilege, or authority
from this contract.** These proposed dependencies and properties require
systemd/SELinux implementation proof; they are not claimed as validated.

### Startup and independent failure

Local filesystems and application data precede identity validation and states
1–10. Normal `multi-user.target`, console, `sl-platformd`, update, rollback and
native recovery do not depend on success. Missing, corrupt, wrong-deployment or
unverifiable content fails without pull, alternate graph, stale namespace or
mutable fallback. Recovery never executes fixture content.

## Runtime authorization boundary

### No Podman socket delegation

Neither `/run/podman/podman.sock` nor the runtime user's rootless Podman socket
is mounted into the Management Plane container. The Podman API is intentionally
not the Management Plane contract because socket possession grants arbitrary
code execution as the engine user and provides no operation-level policy.

The runtime socket is disabled unless a native component demonstrably needs
it. If enabled for implementation tooling, its filesystem and SELinux access
remain exclusive to the runtime identity and it is never network exposed.

### Broker decision

A narrow runtime broker is required **before** the Management Plane may create,
modify or remove general workloads. It is not implemented as part of the
minimal 0.0.4 bootstrap unless acceptance proves a fixed bootstrap operation
cannot be expressed safely through the fixed CoreOS-owned systemd lifecycle.

The future broker:

- runs without host root, normally as the runtime identity or a more narrowly
  separated identity;
- exposes typed workload operations, not Podman CLI flags or arbitrary OCI
  specifications;
- authenticates the Management Plane and authorizes each operation;
- validates image identity, mounts, namespaces, ports, devices, resources and
  labels against policy;
- owns no machine-level capability; and
- calls `sl-platformd` only through separately authorized Platform methods when
  a true machine operation is required.

`sl-platformd` must not become a Podman proxy. The broker must not become a
second privileged machine daemon. The exact broker process/API belongs to the
0.0.5 Management Plane contract.

In 0.0.4 the authorization boundary is deliberately closed: the minimal
container has no runtime-control interface, and the selected CoreOS-owned
bootstrap definition selects the only fixture and deployment-owned content it may run.

## SELinux and privilege model

### Required domains and labels

The design keeps four distinct label roles:

1. a dedicated management-container process domain;
2. the root-owned verifier domain `sl_management_verify_t`;
3. a container root-filesystem/image file type used by Podman; and
4. a dedicated persistent management-data type.

Persistent data receives deterministic policy file contexts or a bounded
CoreOS-controlled initial labeling operation. Existing bind sources are not
labeled by `SecurityLabelFileType`; persistent mounts prohibit `:z` and `:Z`.
Generic `container_t` must be denied even when deliberately assigned the same
MCS categories, making type enforcement primary and MCS defense in depth.

Container-domain templates are experimental inputs, not least-privilege proof.
Phase 1 must inspect their expanded loaded-policy permissions and prove the
exact rootless transition, entrypoint access, type-request spoofing denial and
runtime/systemd/recovery access. If inherited permissions or runtime authority
exceed the contract, stop for architecture review.

Engine storage, bootstrap configuration, container rootfs, management data and
recovery metadata retain distinct types. No implementation may use
`label=disable`, permissive domains, container-loaded policy, enforcement
changes, generic `var_t`/`var_lib_t` access or blind `audit2allow` output.

### Host capability, filesystem, configuration and credential boundary

The runtime account and container receive no host capabilities. `newuidmap` and
`newgidmap` are trusted only for persisted subordinate mappings and are
attributable evidence.

The prohibition on host root, `/proc`, `/sys`, `/run`, `/etc`, `/usr`, `/boot`,
`/sysroot`, bootc, OSTree, journals, recovery metadata, devices and runtime
sockets remains in force for container-visible mounts. Candidate C has one
narrow exception: CoreOS supplies the exact deployment-owned
`/usr/lib/signallayer/management-rootfs` as the container root. It is not a host
`/usr` volume. Resolution rejects symlink/mount substitution and exposes only
manifested rootfs entries. The source is root-owned, deployment-immutable,
read-only and has no `:O` or caller-selected overlay.

Writable paths are exact tmpfs mounts and one typed application-data mount.
Data is `nodev,nosuid,noexec`, outside PATH/loader/plugin/bootstrap searches and
never mounted over executable/configuration content. Interpreting persistent
data as code or privileged configuration is outside D1 and requires amendment.

The 0.0.4 fixture requires no registry or platform secret. Future credentials
must use exact root-owned credential mechanisms, never immutable rootfs/image,
Podman arguments, general environment, application data, logs, evidence bundles
or writable user configuration. Credential files are mounted only to an exact
consumer path, excluded/redacted from content evidence, bounded by ownership,
mode and SELinux, and never retained in disposable graph/runroot. Missing
credentials fail closed without fallback. Tests scan argv, environment, mounts,
logs and preserved evidence and use canary credentials to prove non-exposure.

## Persistent-state model

| State | Location/selection | Authority | Lifecycle |
| --- | --- | --- | --- |
| Bootstrap definition and trusted-reset code | immutable `/usr`, root-owned system units | CoreOS/root | deployment-owned |
| Runtime identity and subordinate maps | `/etc` plus root-owned recovery record | CoreOS/root | machine-persistent; stable across A→B→A |
| Candidate C rootfs and expected manifest | `/usr/lib/signallayer/management-rootfs` in each deployment | CoreOS/root | immutable; selected with booted deployment |
| Candidate C Podman graph/database/runroot | exact paths beneath root-owned runtime-state parent | runtime UID after creation; reset by root | disposable at every trusted launch |
| Candidate B immutable OCI store and manifest | deployment-owned `/usr` path | CoreOS/root | immutable; selected with booted deployment |
| Candidate B writable graph/database/runroot | exact paths beneath root-owned runtime-state parent | runtime UID after creation; reset by root | disposable at every trusted launch |
| Management application data | `/var/lib/signallayer/management/` | management domain/field owner | persistent, typed, versioned and backed up |
| Reset transaction and evidence | `/var/lib/signallayer/runtime-recovery/` | CoreOS/root | minimal, fsynced, never container-writable |

No persistent Podman compatibility-epoch graphroot is required by this Pass 2
contract. Candidate C must prove that graph metadata cannot select executable
content. Candidate B must prove clean reconstruction for each launch and across
A→B→A. Application-data schema compatibility remains separate from Podman
state and must fail before activation when incompatible.

The runtime UID can corrupt its live disposable state and persistent
application data. D1 promises that unauthorized executable substitution in
those locations cannot survive a verified trusted reset. It does not promise
application-data integrity or availability. Recovery preserves and isolates
evidence, never performs unbounded deletion, and never removes application data.

## Content identity, release trust and update model

### Developer-preview provenance

The following identities are distinct and must not be collapsed:

- source revision and clean-tree state recorded by the release workflow;
- OCI config/image ID, manifest digest and verified labels when an OCI artifact
  exists;
- Candidate C's independently generated rootfs content manifest or Candidate
  B's immutable-store manifest;
- the bootc deployment identity that supplies the immutable content;
- publisher authentication; and
- cryptographic attestation.

PR #34's release wrapper and evidence record bind an inspected local image to a
recorded source revision on a trusted build host. They do not authenticate a
publisher or resist a malicious build-host administrator. The 0.0.4 developer
preview accepts that limitation (D3). Digest/hash checks provide content
identity relative to recorded expectations; they do not create cryptographic
provenance. The expected-content manifest is generated during the controlled
CoreOS build, reviewed with release evidence and measured again offline, but
inherits the same trusted-build-host assumption.

### Deployment selection and offline behavior

Candidate C selects only the rootfs shipped by the currently booted CoreOS
deployment. Candidate B selects only the immutable store and recorded identity
shipped by that deployment. Normal boot performs no registry lookup, tag
resolution or pull. Wrong-deployment content, missing content, manifest
mismatch or verification failure leaves the bootstrap failed and CoreOS
operational.

A→B→A must demonstrate that each boot selects that deployment's rootfs/store
and expected manifest, uses stable identity mappings, reconstructs disposable
state, preserves application data and never opens or reuses the other
deployment's mutable runtime state. The fixture content in A and B must differ
in an independently measurable way so the test cannot pass while selecting the
wrong deployment. Existing bootc staging, manual activation
and rollback remain the only machine-deployment authority.

### Management fixture lifecycle

0.0.4 installs one non-product fixture. It implements no automatic image
updates, self-update, workload orchestration or independent network retrieval.
For Candidate C, fixture content changes only with CoreOS deployment. For
Candidate B, the immutable OCI store changes only with CoreOS deployment.
General OCI transport, image lifecycle, signature policy and workload admission
are deferred to 0.0.5.

## Failure and recovery model

| Failure | Required behavior | Recovery owner |
| --- | --- | --- |
| Fixture crash | Re-entry starts state 1; no stale-state reuse | reset unit/system manager |
| Primary/subordinate/helper survivor or respawn | Maintain inhibit; preserve attributable/ambiguous evidence; never launch/trust | reset unit + verifier |
| Enabled login/linger/user-manager/timer/activation/transient-unit authority | Contract violation; launch blocked | reset unit + system manager |
| Runtime/subordinate IPC/keyring/temp/unexpected file or mount | Attribute using cgroup/ancestry/maps/namespaces/ownership; exact quarantine or block; unrelated objects and application data untouched | reset unit + verifier |
| Stale namespace/mount or out-of-cgroup holder | Preserve; never reuse; block while holder or attribution ambiguity remains | reset unit + verifier |
| Verifier manual/stale/mismatched/interrupted result | Reject result; contained teardown; never publish trusted | reset unit + system manager |
| Wrong/missing deployment rootfs/store | Reject before launch; no registry/graph fallback | reset unit |
| Content/config-open mismatch | Stop fixture, preserve evidence, publish failed | reset unit/root verifier |
| Interrupted reset/power loss | Quarantine incomplete disposable state as needed and restart at state 1; never resume an intermediate state | reset unit |
| Full disk/resource exhaustion | Bounded failure; native reserve remains | native recovery |
| SELinux/storage/network fallback | Refuse candidate; never weaken confinement | reset unit/operator |
| Application-data corruption | Preserve/report; do not claim data integrity | application recovery |
| CoreOS A→B→A | Select booted deployment content, reset disposable state, preserve maps/data | reset unit + existing bootc |
| Podman absent/broken | Console, status, update, rollback and recovery remain usable | CoreOS |

The reset executor preserves evidence and application data, resolves bounded
paths without following attacker symlinks and never performs unbounded cleanup.
Quarantined disposable state and evidence use fixed count/size/age retention
limits selected before implementation; exceeding a limit fails closed and
preserves the newest attributable evidence without touching application data.
It has no public interface. The Management Plane gains no reset, Podman,
systemd, host-root or machine authority. `sl-platformd` is unchanged.

## Threat model

### Attacker classes and guarantee

| Class | Capability | Contract guarantee |
| --- | --- | --- |
| A. Container process | Controls fixture and writable mounts in its namespaces | Cannot mutate CoreOS/bootstrap/rootfs or persist executable substitution across trusted reset; native recovery remains independent |
| B. Native `sl-management` process | Controls current UID session and UID-writable disposable/application state | In-session integrity not promised; trusted reset closes spawn paths, removes survivors and rebuilds state before trust |
| C. Host root/trusted build | Can replace policy, deployment, evidence or manifests | Outside D1; developer preview claims no protection |

Executable integrity covers rootfs, entrypoint, interpreter/loader, libraries,
executable configuration, arguments/environment and all code-selection inputs.
Persistent application data has no D1 integrity guarantee and cannot redirect
bootstrap or executable selection.

### Per-threat security matrix

| Threat | Preventive controls | Evidence | Failure behavior | Residual risk |
| --- | --- | --- | --- | --- |
| Container escape | Rootless namespace, seccomp, zero caps, NNP, SELinux, no devices/host namespaces | UID maps, caps, seccomp, labels, namespace/mount inventory | Stop fixture; native recovery remains | Kernel/runtime vulnerability |
| Host privilege escalation | No host UID 0, privileged mode, runtime socket, setuid fixture or machine API | Maps, sockets, executable/capability manifest, denial probes | Deny/stop/preserve | Trusted kernel/helpers |
| Host filesystem access | Exact rootfs/data/tmpfs only; narrow C exception | Root-side mountinfo and read/write negatives | Deny without relabel/broad grant | Explicitly mounted data exposed |
| SELinux bypass | Enforcing dedicated domains/types; no disable/permissive | Loaded-policy query, contexts, equal-MCS negative | Candidate rejected | Policy/runtime/kernel defect |
| Podman API abuse | No socket/API and no user manager | Filesystem/kernel/API/container-root socket probes | No control path | Class-B live-session control |
| Malicious fixture content | Immutable deployment content, independent manifest/oracle | Effective content, entrypoint/config and deployment identity | Reject/stop; no fallback | Trusted build may be malicious |
| Unauthorized workload creation | One fixed unit/fixture; no adapter mutation | Process/container inventory equals allowlist | Impossible/denied | Future 0.0.5 fault domain |
| Credential exposure | No fixture secret; exact future credentials; no argv/env/log/data retention | Canary scans of argv/env/mounts/logs/evidence | Fail closed and redact/preserve | Explicitly delegated secret visible to consumer |
| Persistent executable tampering | Root-owned content/config; disposable runtime; closed spawn surface | Reset transaction, file-open evidence, manifest/oracle | Quarantine/block | Application data may be corrupt |
| Denial of service | cgroup/storage/start/log-rate limits and CoreOS reserve | cgroup/storage/service/log metrics and recovery probes | Stop/degrade fixture; CoreOS responsive | Shared kernel/storage contention |
| Bootstrap compromise | Root-owned fixed reset unit/launcher; no public API; config injection denied | Unit/executable hashes, loaded unit, config opens, override negatives | Inhibit and fail | Root compromise outside boundary |
| Supply-chain compromise | Recorded source/artifact/content/deployment identities | PR #34 evidence, manifests and offline measurements | Reject mismatch | Unsigned trusted build host/class C |

### Single runtime-UID fault domain

All authorized Podman/conmon/pause/container processes share one runtime UID.
Class-B compromise can control that live session even without host root. 0.0.4
limits the UID to one fixed fixture and relies on trusted reset for persistence.
Before 0.0.5 introduces workload mutation, the broker/identity design must
decide whether control and workloads require separate identities/stores. This
warning is deferred, not resolved by Candidate C.

### Residual assumptions

Kernel, systemd, SELinux policy, Podman/crun/conmon, ID-map helpers and immutable
CoreOS content are trusted. Physical/pre-OS and class-C compromise are outside
scope. Resource exhaustion cannot be eliminated. Future engine delegation is a
new authority boundary.

## Acceptance test contract

Acceptance uses reviewed source, genuine x86_64 KVM/OVMF, disposable overlays
and preserved serial/QMP/journal/audit/policy evidence. Every critical property
has a deliberate failing fixture. Startup, Podman inspect, unchanged store,
EROFS or absence of AVCs alone is insufficient.

### Static, build and offline gates

- exact pinned package/configuration/source inventory and PR #34 release evidence;
- deterministic Candidate C rootfs or Candidate B immutable-store manifest;
- fixed reset, runtime and verifier units/executables; no public D-Bus/socket/CLI,
  caller arguments, install targets or automatic runtime restart; exact
  `Wants=`/`Before=`/`After=` ordering, `RefuseManualStart`, descriptor guard,
  `User=sl-management`, `Delegate=cpu cpuset io memory pids`,
  `KillMode=control-group`,
  `FileDescriptorStoreMax=0` and transaction binding;
- systemd verification and loaded-unit dependency/override/spawn-source/transient-unit-authorization inventory;
- reviewed CoreOS source-inventory entries and product-owner implementation
  approval for the new reset, runtime and verifier units as required by
  `ENGINEERING.md`;
- account/map collision, partial-state and interrupted-provisioning fixtures;
- SELinux compile, expanded-template/allow queries, entrypoint/type transition,
  equal-MCS generic-container denial and no broad runtime grant;
- exact configuration/environment/search-path allowlist and root-side file-open
  evaluator with unexpected-open fixtures;
- manifest/oracle parser tests for regular files, links, ownership, labels,
  xattrs, whiteouts, opaque directories and excluded paths;
- explicit exclusion of sockets, privilege, broad mounts, host namespaces,
  fallback drivers/helpers, unpinned content and general cleanup; and
- attributable source, OCI (when B), content manifest, deployment and qcow2 identities.

### Independent running-content oracle

The expected manifest is generated independently of Podman from deployment
content. It records each regular-file digest; path/type; symlink target;
hardlink equivalence; UID/GID; mode; SELinux context; relevant xattrs including
capabilities; and exact dynamic-path exclusions. Unexpected devices, sockets,
FIFOs, setuid/setgid or capabilities fail unless approved.

Root identifies the workload PID through fixed systemd InvocationID,
cgroup/ancestry and start time, not image metadata; stabilizes it for
measurement; records UID maps/namespaces, `/proc/<pid>/exe`, root and mountinfo;
hashes effective content; and revalidates PID identity before release. Root-side
file-open evidence identifies consumed configuration independently of Podman.

For C, prove exact deployment-rootfs origin, read-only mount, no overlay upper
and manifest equality. For B, also validate immutable lowers, upper/work origin,
whiteout/opaque semantics, no trusted-layer materialization and effective merged
manifest. Substitution fixtures cover executable, loader/library, symlink,
hardlink, xattr/label, mount, metadata/layer, whiteout and opaque directory.

D1–D7 settle their listed directions, including D4's strengthened fail-closed

## Stop conditions

Stop for architecture review if Candidate C depends on attacker-persistent
image selection, an unverified writable overlay or a broad host `/usr` mount;
if Candidate B requires unsupported rootless-store behavior, persistent trusted
metadata, `force_mask=shared`, VFS/FUSE fallback or broad DAC/SELinux grants;
if teardown cannot safely attribute primary/subordinate/helper processes and
resources or detect out-of-cgroup namespace holders; if continuous spawn
exclusion cannot be enforced through state 10; if the verifier can activate
independently, survive teardown or publish trust; if persistent data can select
executable content; if the content oracle cannot distinguish a supplied
substitution fixture; or if Podman failure blocks native CoreOS recovery.

Missing experimental evidence is reported as **UNPROVEN**, never waived. One
candidate may fail without invalidating the other, but neither becomes the
0.0.4 mechanism without its complete applicable matrix and human approval.

## Approval gate

This adopted contract incorporates approved D1–D7, including the strengthened

experiment still requires separate explicit authorization. Contract approval
freezes the threat-model guarantee, authority boundaries, rootfs exception, trusted-reset outcomes,
release scope and acceptance matrix; it does not preselect unproven Fedora

Implementation changes that alter authority, persistent state, executable
