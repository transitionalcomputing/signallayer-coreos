## Validated capabilities

- UEFI boot under genuine x86_64 KVM into a healthy systemd system with
  NetworkManager networking.
- Immutable, read-only root and `/usr` with composefs enabled.
- Confined Platform API 0.3 services with local `corectl` status, fixed
  root-only update, rollback and reboot methods, and no caller-controlled
  command or unit name.
- Explicit update staging, operator-requested activation, retained-deployment
  rollback selection while the registry is unavailable, and exact restoration
  of the original deployment.
- Unprivileged Session1 status aggregation using schema 0.4.
- A trusted local appliance console on `tty1` and `ttyS0` with no Linux login,
  shell, arbitrary command execution or general machine-mutation authority.
- Unprivileged authentication with password, one-time pairing, recovery-key
  password recovery and enrollment reset behavior.
- Authenticated, LAN-only, read-only HTTPS management with bundled assets,
  self-signed TLS identity, on-link admission and fail-closed withdrawal when
  authoritative session or network state disappears.

## Acceptance evidence

The final qcow2 passed both maintained release gates on Fedora 44:

- Phase 5E integrated acceptance: **75/75 PASS**, genuine KVM, two vCPUs,
  clean shutdown and unchanged source disk.
- Complete A -> staged B -> booted B -> offline rollback -> exact A lifecycle:
  **45/45 PASS**, genuine KVM, four vCPUs, three distinct boots, clean
  shutdown and unchanged source disk.

The lifecycle also verified exact OCI deployment identities, converged
Platform/Session1 status, enforcing SELinux without unexpected relevant AVCs,
healthy networking and systemd state, immutable mounts, and rejected writes to
the protected system trees.

## Known limitations

- Only x86_64 KVM with OVMF UEFI was validated. Secure Boot, physical hardware
  and other architectures were not validated.
- The qcow2 retains `localhost/signallayer-coreos:0.0.3` as its bootc origin.
  Lifecycle acceptance used a host-local development registry. Public registry
  provisioning, TLS and authentication remain operator responsibilities.
- Update and rollback activation require explicit operator reboots. There is no
  automatic health-triggered rollback or boot-attempt policy.
- There is no installer, separate recovery environment, Linux login, SSH
  provisioning workflow or general-purpose local shell.
- Remote management is single-operator, LAN-only and read-only. It uses a
  machine-generated self-signed certificate whose fingerprint the operator
  must verify. Remote update, rollback, reboot and command execution are absent.
- The enrolled-console password check is enforced by the console and `sl-authd`;
  Platform authorizes the confined console service identity. Platform-verified
  authentication proofs are deferred.
- Pre-OS console access remains machine-owner access. GRUB editing and
  command-line recovery bypasses are not locked down in 0.0.3.
- On-link admission is enforced in the application. A second nftables layer is
  deferred, as are the broader adversarial reviews listed in the frozen 0.0.3
  remote-management contract.
- The durable management-plane UI and managed Podman workload model are
  deferred; the bundled read-only web interface is transitional.
- Session1 status is unavailable while `sl-authd` is unavailable. This known
  coupling fails closed.
- Composefs `verity=false` remains inherited and accepted. Fedora's `install_t`
  is the intentionally trusted deployment-mutation domain.

The qcow2 is an evaluation/development artifact, not a production installation
workflow.
